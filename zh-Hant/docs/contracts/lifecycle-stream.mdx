以每次狀態轉換一個 JSON 影格的方式，跟隨一個執行中的工作階段。

一個終止信封無法描述整個工作階段，因此 `dev`、`start` 與 `preview` 會為每一次生命週期轉換串流輸出一個 schema-1 影格。每個影格本身就是獨立成行的一個完整[結果信封](/zh-Hant/docs/contracts/result-envelope)。

## 開啟這道串流

這道串流由 `EXTENSION_OUTPUT` 環境變數決定。把它設為 `json` 或 `ndjson`，影格就會獨佔 stdout：

```bash
EXTENSION_OUTPUT=ndjson npx extension@latest dev ./my-extension --browser chromium --no-browser
```

串流開啟期間，原本共用 stdout 的人類可讀文案會移到 stderr。錯誤文案永遠留在 stderr，機器模式絕不會隱藏失敗。

## 影格狀態

| 狀態             | `ok`  | 何時送出                                                                    |
| ---------------- | ----- | --------------------------------------------------------------------------- |
| `starting`       | true  | 只有一次，工作階段開始時，也就是設定載入完成、編譯器已建立之後。帶有 `requestedPort` 與實際綁定的 `port`。 |
| `compiled`       | true  | 第一次成功編譯。帶有 `assets` 與 `durationMs`。                             |
| `recompiled`     | true  | 之後每一次成功編譯。                                                        |
| `compile-failed` | false | 一次編譯帶著錯誤結束，無論是第一次或之後。                                  |
| `ready`          | true  | 本次工作階段的 `ready.json` 已寫入磁碟時。之後的編譯清除了 `ready-failed` 或 `load-refused` 時會再次送出。從 4.1.41 之後的版本起，`dev` 重新啟動成功後也會再次送出，並帶 `value.restarted: true`。 |
| `browser-exited` | false | 瀏覽器在工作階段中途結束，見下文。                                          |
| `restart-failed` | false | 從 4.1.41 之後的版本起。某次重新啟動無法建置下一個 bundle，因此先前的建置繼續提供服務，`value.serving` 為 `true`。`error.code` 是該失敗自己的錯誤碼，或 `E_DEV_SERVER_START`。再次儲存變更的檔案即可重試。 |
| `load-refused`   | false | 瀏覽器拒絕了擴充功能。工作階段繼續進行，並在下一次編譯時再次提供它。 |
| `ready-failed`   | false | 從 4.1.41 之後的版本起。工作階段仍在進行時 `ready.json` 回報 `error`，例如啟動失敗。下一次編譯會再試一次。 |
| `warning`        | true  | 從 4.2.0 之後的版本起。工作階段在兩次編譯之間警告過的事情，一旦得知就立即寫入，例如擴充功能始終沒有確認的重新載入。`value.code` 與 `value.message` 說明它，`warnings` 中有一筆紀錄。之後的影格不會重複它。 |
| `failed`         | false | 結束這次執行的工作階段層級失敗，例如伺服器始終沒能綁定、重新啟動的下一個伺服器無法啟動，或停止超過了關閉時限。 |
| `usage`          | false | 瀏覽器啟動拒絕了你設定的值時的最後一個影格，例如有問題的 `--chromium-binary` 固定路徑。 |
| `stopped`        | 視情況 | 最後一個影格。工作階段以結束代碼 `0` 自行結束時為 `ok: true`。被 `SIGINT` 這類訊號停止時為 `ok: false`，帶 `E_INTERRUPTED` 與 `value.signal`。 |

每個影格的 `value` 都帶有工作階段身分：`command`、`browser`、`distPath`、`pid`、`port`，以及已知時的 `readyPath`、`eventsPath`、`runId`、`instanceId` 與 `toolchainVersion`。

`failed`、`usage` 與 `stopped` 是終止狀態。終止影格表示處理程序正在結束，串流在它之後不再寫入任何內容，因此讀到第一個終止影格就停止。其他每個 `ok: false` 影格都讓工作階段繼續進行。當 CLI 知道該錯誤碼的解決方法時，`failed` 或 `usage` 影格會把它放在 `hint` 中。

只有這三種會結束串流。讀取端忽略它不認得的狀態並繼續讀取，所以之後版本新增的狀態不會讓它停下。

從 4.2.0 之後的版本起，終端機回報的兩種重新載入失敗，也就是擴充功能始終沒有確認的編譯與一直沒有回來的擴充功能，也會以帶 `W_RELOAD_NOT_APPLIED` 的 `warning` 影格送達。終端機文字不帶代碼。

在工作階段開始之前就被拒絕的執行只會送出一個 `failed` 影格，不會有 `starting` 影格。缺少 manifest、設定檔載入失敗，以及遠端 URL 沒有可用的封存檔，都會以這種方式結束。

## 編譯失敗

`compile-failed` 影格會把編譯器輸出放在 `value.output` 裡，因此你永遠不必去刮 stdout。這段輸出已去除 ANSI 控制碼，並以 2000 個字元為上限。當上限把它截斷時，該影格會設定 `truncated: true`。

一次工作階段中的第一次失敗使用錯誤碼 `E_FIRST_COMPILE`，之後每一次都使用 `E_COMPILE`。

該影格也會帶著 `error.details`，每條診斷一個條目，各自帶有錯誤碼、檔案和位置，錯誤排在前面，結構見[結果信封](/zh-Hant/docs/contracts/result-envelope)中的「編譯診斷」一節。清單上限為 20 條，當輸出或清單任一被截斷時，都會設定 `truncated: true`。

```jsonl
{"schema":1,"ok":true,"command":"dev","status":"starting","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"requestedPort":8080},"error":null,"warnings":[]}
{"schema":1,"ok":true,"command":"dev","status":"compiled","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4","assets":12,"durationMs":841},"error":null,"warnings":[]}
{"schema":1,"ok":true,"command":"dev","status":"ready","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4"},"error":null,"warnings":[]}
{"schema":1,"ok":false,"command":"dev","status":"compile-failed","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4","output":"ERROR in ./content/scripts.ts\nModule parse failed: Unexpected token (12:3)","durationMs":204},"error":{"code":"E_COMPILE","message":"A recompilation failed after a change.","details":[{"code":"E_CONTENT_SCRIPT_SYNTAX","message":"Module parse failed: Unexpected token (12:3)","file":"content/scripts.ts","line":12,"column":3,"severity":"error"}]},"warnings":[]}
```

## ready 遵循契約

`ready` 影格在送出之前會先讀取 `ready.json`。編譯可能成功，而瀏覽器卻拒絕了這個擴充功能，發生這種情況時契約會停留在 `error`。

工作階段仍在進行時，串流接著會發出 `ready-failed` 影格。瀏覽器拒絕了擴充功能時，發出的是 `load-refused`。兩者都不會結束工作階段，之後清除該錯誤的編譯會再次寫出 `ready`。只有當處理程序結束時 `ready.json` 仍回報該錯誤，契約錯誤才會變成 `failed` 影格。

`error.code` 是啟動器蓋上的錯誤碼，否則就是契約狀態對應的錯誤碼。例如 `browser_launch_failed` 對應 `E_BROWSER_LAUNCH`，被拒絕的載入對應 `E_EXTENSION_LOAD_REFUSED`。`E_READY_ERROR_STATUS` 只留給沒有自身錯誤碼的狀態。`value.readyCode` 指出契約自身的錯誤 id。

瀏覽器根本沒有啟動時，會送出這個影格，`value.readyCode` 為 `browser_launch_failed`。Firefox 的除錯器始終沒有回應時，視為啟動失敗。瀏覽器結束時送出的則是 `browser-exited` 影格，見下文。

`--chromium-binary` 或 `--gecko-binary` 固定的執行檔有問題時，`readyCode` 同樣是 `browser_launch_failed`，但其影格帶 `status: "usage"` 與 `error.code: "E_BROWSER_BINARY_INVALID"`，這也是每個命令對這種固定路徑給出的代碼。

Chromium 的 `dev` 工作階段在瀏覽器起來之後 CDP 連線失敗時,仍然會送出 `ready`,因為瀏覽器在執行。該影格會把故障放在 `warnings` 裡,形式為 `W_CDP_...: message`,與契約蓋上的 `cdpFaultCode` 和 `cdpFaultMessage` 是同一對值,見 [ready.json](/zh-Hant/docs/contracts/ready-json)。在故障修復前,reload 與 HMR 無法接上。

## 瀏覽器結束

一個背景監看器每秒輪詢一次 `ready.json`，尋找啟動器寫下的結束戳記。當 `browserExitedAt` 出現時，串流會發出一個 `browser-exited` 影格。

影格的錯誤碼取決於契約中的證據：

- `E_PROFILE_LOCKED`：契約顯示設定檔被鎖定。瀏覽器根本沒有啟動，另一個工作階段正佔用該設定檔。
- `E_BROWSER_LAUNCH`：其餘所有非預期的結束。

當契約中有這些欄位時，影格的 `value` 會帶有 `exitCode`、`exitSignal` 與 `browserExitedAt`。當機沒有結束代碼，只有 `SIGTRAP` 這類訊號。

從 4.1.41 之後的版本起，`browser-exited` 或 `ready-failed` 影格的 `hint` 以 CLI 對該錯誤碼已知的解決方法開頭，接著說明工作階段繼續進行。對於 `E_PROFILE_LOCKED`，解決方法是關閉開著該設定檔的瀏覽器，或傳入 `--profile <path>`。

## 重新啟動與關閉

從 4.1.41 之後的版本起，下一個 bundle 無法建置的重新啟動會送出一個 `restart-failed` 影格，舊的伺服器繼續提供服務。如果舊伺服器停止後下一個伺服器無法啟動，串流會送出 `failed`，處理程序以 `1` 結束。

從 4.1.41 之後的版本起，`dev` 重新啟動成功後，新伺服器的第一次編譯通過時會再次寫出 `ready`。該影格的 `value` 帶有 `restarted: true`。在那之前，串流照常寫出編譯影格。

關閉有 10 秒可以完成，之後處理程序以 `1` 結束。在第一次 `Ctrl+C` 超過一秒之後再按一次，也會立即強制以 `1` 結束。被強制的關閉絕不會回報成功。

從 4.1.41 之後的版本起，如果之前沒有寫出終止影格，超過這個時限的停止會以帶 `E_SHUTDOWN_TIMEOUT` 的 `failed` 結束串流。自動結束期限觸發的停止就是一個例子。該影格的 `value` 帶有 `exitCode` 與 `shutdownTimeoutMs`。由訊號觸發的停止保留它的 `stopped` 影格。

從 4.2.0 之後的版本起，`preview` 與 `start` 也以同樣的方式結束串流。收到 `SIGINT` 或 `SIGTERM` 時，最後一個影格是帶 `E_INTERRUPTED`、`value.signal` 與 `value.browsers`（這次執行面向的瀏覽器）的 `stopped`，接著執行以 `0` 結束。

從 4.2.0 之後的版本起，在指令寫出任何影格之前到達的訊號，仍會以一個帶 `E_INTERRUPTED` 與 `value.signal` 的 `stopped` 影格結束串流。`SIGINT` 時執行以 `130` 結束，`SIGTERM` 時以 `143` 結束。

以 `0` 以外的結束代碼結束的工作階段同樣以終止影格結束。`ready.json` 中有錯誤時，該影格帶有那個錯誤的錯誤碼。否則就是帶 `E_INTERNAL` 與 `value.exitCode` 的 `failed`。
