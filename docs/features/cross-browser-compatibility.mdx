Extension.js handles browser-specific setup during development and build. You
produce runtime-correct outputs for Chromium and Gecko (Firefox engine) targets
from one project.

## Cross-browser extension development

Cross-browser extension development means writing one extension that ships to Chrome, Edge, and Firefox without forking the codebase. Extension.js compiles a single project into per-browser artifacts (`dist/chrome`, `dist/edge`, `dist/firefox`) and filters the manifest for the active target. The reload loop, runtime APIs, and packaging all match the browser you are debugging.

Use one `manifest.json` and target specific browsers or custom binaries. Enable polyfills when you need `browser.*` API compatibility in Chromium-family targets.

## Chrome and Firefox extension compatibility

Chrome and Firefox extensions share most of the WebExtensions surface but differ in three places that matter every day:

- **Background scripts:** Chrome (Manifest V3) requires `background.service_worker`. Firefox uses `background.scripts` with non-persistent event pages. Extension.js translates between the two shapes in both directions, so either spelling works from one manifest.
- **Runtime API namespace:** Firefox supports `browser.*` natively. Chromium uses `chrome.*`. Pass `--polyfill` to bridge the gap on Chromium targets.
- **Permissions and content security policy (CSP):** Browsers evaluate some `permissions` and `host_permissions` entries differently. Keep browser-specific values behind prefixed manifest keys instead of feature-detecting at runtime.

## Browser-specific manifest fields

Browser-specific manifest fields are how Extension.js keeps a single `manifest.json` working across browsers. At compile time, Extension.js filters prefixed keys (`chromium:`, `chrome:`, `edge:`, `firefox:`, `gecko:`) to the active target. Unprefixed keys apply everywhere. See [Browser-specific manifest fields](/docs/features/browser-specific-fields) for the full prefix list.

## How it works

### 1) Choose a browser target

Choose where you want to run your extension.

Use `--browser` for common targets, or pass a custom browser binary.

<CodeGroup>

```bash npm
extension dev --browser firefox
```

```bash pnpm
extension dev --browser firefox
```

```bash yarn
extension dev --browser firefox
```

```bash bun
extension dev --browser firefox
```

```bash deno
extension dev --browser firefox
```

</CodeGroup>

<CodeGroup>

```bash npm
extension dev --chromium-binary /Applications/Brave\\ Browser.app/Contents/MacOS/Brave\\ Browser
```

```bash pnpm
extension dev --chromium-binary /Applications/Brave\\ Browser.app/Contents/MacOS/Brave\\ Browser
```

```bash yarn
extension dev --chromium-binary /Applications/Brave\\ Browser.app/Contents/MacOS/Brave\\ Browser
```

```bash bun
extension dev --chromium-binary /Applications/Brave\\ Browser.app/Contents/MacOS/Brave\\ Browser
```

```bash deno
extension dev --chromium-binary /Applications/Brave\\ Browser.app/Contents/MacOS/Brave\\ Browser
```

</CodeGroup>

Use a binary path that matches your OS:

- **macOS**: `/Applications/Brave Browser.app/Contents/MacOS/Brave Browser`
- **Linux**: `/usr/bin/brave-browser` (or another Chromium-based browser binary)
- **Windows**: `"C:\\Program Files\\BraveSoftware\\Brave-Browser\\Application\\brave.exe"`

When you pass a binary, Extension.js maps it to a browser engine target:

- `chromium-based` for `--chromium-binary`
- `gecko-based` for `--gecko-binary`

### 2) Compile with browser-specific manifest filtering

During compilation, Extension.js includes only the manifest fields for your selected browser.

For example:

```json
{
  "chromium:background": {
    "service_worker": "sw.js"
  },
  "firefox:background": {
    "scripts": ["sw.js"]
  }
}
```

For Chromium-family targets, Extension.js uses prefixes like `chromium:`, `chrome:`, and `edge:`.  
For Firefox-family targets, Extension.js uses `firefox:` and `gecko:`.

<Note>
  See [Browser-specific manifest fields](/docs/features/browser-specific-fields)
  for full details on prefixed manifest fields.
</Note>

#### Background translation is bidirectional

You do not need prefixed background keys for the common case. Extension.js translates a plain MV3 `background` in both directions:

- A Gecko build that finds `background.service_worker` and no `background.scripts` repoints the background at the emitted bundle through `scripts`. It drops `service_worker` and `type`, which Firefox rejects.
- A Chromium MV3 build that finds `background.scripts` fills `service_worker` from the first script when no worker is set.

In the Chromium direction, `scripts` is always removed from the output. Chromium MV3 rejects the whole extension whenever `background.scripts` is present, even beside a valid `service_worker`, so the key can never ship in a Chromium build.

### 3) Output per browser target

Extension.js writes each target to its own build folder:

- `dist/chrome`
- `dist/edge`
- `dist/firefox`
- `dist/chromium` (the default target)
- `dist/chromium-based` (custom Chromium engines)
- `dist/gecko-based` (custom Gecko engines)

This keeps your builds organized and easier to ship in CI.

### 4) Optional `browser.*` polyfill for Chromium targets

If your code uses `browser.*`, enable `--polyfill` for Chromium-family targets:

<CodeGroup>

```bash npm
extension build --browser chrome --polyfill
```

```bash pnpm
extension build --browser chrome --polyfill
```

```bash yarn
extension build --browser chrome --polyfill
```

```bash bun
extension build --browser chrome --polyfill
```

```bash deno
extension build --browser chrome --polyfill
```

</CodeGroup>

When enabled, Extension.js uses `webextension-polyfill` (Mozilla's `browser.*` compatibility library) for non-Firefox targets.  
Extension.js skips this step for Firefox because Firefox already supports `browser.*` natively.

The polyfill module resolves from your project first, then from the bundled Extension.js dependency. Package managers may hoist `webextension-polyfill` to your project root, and a copy you installed yourself wins over the bundled one. When no copy resolves at all, the build prints a warning and continues without the polyfill instead of failing.

## Best practices

- **Keep one codebase**: Put browser differences in prefixed manifest fields when possible.
- **Build one target at a time**: Generate dedicated artifacts (`dist/<browser>`) for each browser in continuous integration (CI).
- **Use `--polyfill` when needed**: `build` leaves it off until you pass `--polyfill`, while `dev` and `start` apply it by default. Pass `--no-polyfill` there when your code does not depend on `browser.*`.
- **Check API support early**: Use [MDN WebExtensions docs](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions) before relying on browser-specific APIs.
