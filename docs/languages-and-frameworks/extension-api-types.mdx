Extension.js compiles TypeScript with SWC, which strips types and never checks them. Type checking is a separate step that you run with `tsc`. This page covers how that step resolves `chrome.*`, `browser.*`, and `process.env`.

## What Extension.js generates

When a project uses TypeScript, `extension dev`, `extension build`, and `extension start` write an `extension-env.d.ts` file beside `package.json`. It is regenerated on every run, so do not edit it.

The file pulls in the ambient types that the `extension` package publishes:

```ts extension-env.d.ts
/// <reference types="extension/types" />
/// <reference types="extension/types/polyfill" />
```

Those references give you:

| Reference                  | What it declares                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------- |
| `extension/types`          | The `browser` namespace and its `chrome` alias, `process.env` and `import.meta.env` keys |
| `extension/types/polyfill` | The `webextension-polyfill` module, for `import browser from 'webextension-polyfill'` |
| Wildcard modules           | `import` of `.css`, `.module.css`, `.png`, `.svg`, and other assets, plus `?raw` and `?url` imports |

The `EXTENSION_*` environment keys are typed here too. That is why `process.env.EXTENSION_MODE` resolves without extra setup.

A project that installs `@types/chrome` gets a different first reference. The section "Keep @types/chrome" on this page shows it.

When the `extension` package does not resolve from the project, for example a project that only runs the CLI through `npx`, the two references find nothing. The generated file then also carries the wildcard module declarations inline, so stylesheet, image, `?raw`, and `?url` imports still type-check.

## Types that install with Extension.js

The `extension` package lists the three type packages that its references need as dependencies:

| Package                        | What it types             |
| ------------------------------ | ------------------------- |
| `chrome-types`                 | The `browser.*` namespace and its `chrome.*` alias |
| `@types/webextension-polyfill` | The `webextension-polyfill` module |
| `@types/node`                  | `process.env`             |

[`chrome-types`](https://www.npmjs.com/package/chrome-types) is the package that Chrome generates from the Chromium source. Its `browser` is the native namespace, and its methods return promises. `chrome` is an alias of it.

`chrome-types` does not declare the APIs that only Firefox has. Extension.js types Firefox's `browser.sidebarAction` and `browser.browserAction` itself.

They install with `extension`, so `tsc` resolves `chrome.*` and `browser.*` in a new project without an extra install:

```bash
npx tsc --noEmit
```

The build does not need these packages. SWC never reads the types, so the build succeeds with or without them.

## Keep @types/chrome

A project that installs `@types/chrome` keeps it. That package types `chrome`, and `browser` is typed from `webextension-polyfill` as before.

`@types/chrome` and `chrome-types` both declare the `chrome` global, so the two packages cannot load together. The generated `extension-env.d.ts` references one or the other. It references `@types/chrome` when your `package.json` lists that package. It does the same when `node_modules/@types/chrome` exists in the project folder or in a parent folder:

```ts extension-env.d.ts
/// <reference types="extension/types/legacy" />

// This project installs @types/chrome, so it types the extension APIs.
// Remove that package to get chrome-types and the native browser namespace.
/// <reference types="chrome" />

// Polyfill types for browser.* APIs
/// <reference types="extension/types/polyfill" />
```

To move to `chrome-types`:

1. Remove `@types/chrome` from your project.
2. Run `extension dev` or `extension build` once.

To go back to `@types/chrome`:

1. Install `@types/chrome` as a development dependency.
2. Run `extension dev` or `extension build` once.

On the default setup, the `browser` global has the native types. For the `webextension-polyfill` types, import the module:

```ts
import browser from "webextension-polyfill";
```

## Pin your own version

The `extension` package accepts any version of `@types/node` and `@types/webextension-polyfill`. It accepts `chrome-types` 0.1.460 or later. When your project declares one of them, npm, pnpm, and Bun reuse the copy that your project installs.

When your `tsconfig.json` has no `types` array, TypeScript also loads the copy that your project declares. The version in your own `package.json` wins:

```json package.json
{
  "devDependencies": {
    "@types/webextension-polyfill": "^0.12.0"
  }
}
```

## Projects on Extension.js 4.1.18 or older

Before 4.1.19, `extension/types` referenced `chrome` but did not install `@types/chrome`. A project that calls `chrome.*` without its own copy fails `tsc`:

```plaintext
src/background.ts(19,1): error TS2304: Cannot find name 'chrome'.
src/content/scripts.ts(87,30): error TS2503: Cannot find namespace 'chrome'.
```

Upgrade `extension` to 4.1.19 or later. If you stay on an older version, install the package by hand:

<CodeGroup>

```bash npm
npm install -D @types/chrome
```

```bash pnpm
pnpm add -D @types/chrome
```

```bash yarn
yarn add -D @types/chrome
```

```bash bun
bun add -d @types/chrome
```

```bash deno
deno add -D npm:@types/chrome
```

</CodeGroup>

On those versions, `browser` has the type `any` until `@types/webextension-polyfill` is installed. To type `browser.*`, install that package too:

<CodeGroup>

```bash npm
npm install -D @types/webextension-polyfill
```

```bash pnpm
pnpm add -D @types/webextension-polyfill
```

```bash yarn
yarn add -D @types/webextension-polyfill
```

```bash bun
bun add -d @types/webextension-polyfill
```

```bash deno
deno add -D npm:@types/webextension-polyfill
```

</CodeGroup>

## Type errors after an upgrade

Earlier releases installed `@types/chrome` with `extension` and typed `browser` from `webextension-polyfill`. A project that installs `@types/chrome` keeps those types. A project without `@types/chrome` moves to `chrome-types` on upgrade.

After that move, code that passed `tsc` before can show new type errors. For example, `tsc` can report names such as `chrome.tabs.TabChangeInfo` missing.

Install `@types/chrome` to keep the previous types, then run `extension dev` or `extension build` once. Read [Cross-browser compatibility](/docs/features/cross-browser-compatibility) for the runtime side of `browser.*`.

## Keep extension-env.d.ts in the include list

The generated file only helps when TypeScript reads it. The scaffolded `tsconfig.json` names it:

```json tsconfig.json
{
  "include": ["./", "extension-env.d.ts"],
  "exclude": ["node_modules", "dist"]
}
```

When Extension.js writes a `tsconfig.json` for a project that has none, that file carries no `include` array. TypeScript then reads every file under the project folder, so it finds `extension-env.d.ts` anyway. An `include` array of your own that omits the file breaks asset imports and the `browser` global.

From the release after 4.1.39, Extension.js creates the file only when your `tsconfig.json` would read it beside `package.json`. That is the case with no `include` array, with an `include` that covers the project root, or when `include` or `files` names the file. With a narrower `include` such as `["src"]`, the file is not created, so add it:

```json tsconfig.json
{
  "include": ["src", "extension-env.d.ts"]
}
```

A copy that already exists is kept up to date either way. Reformatting it, for example with other quotes or without semicolons, does not trigger a rewrite.

## Symptoms and fixes

| Symptom                                   | Cause                                                 | Fix                                                    |
| ----------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| `Cannot find name 'chrome'`               | Extension.js 4.1.18 or older, and no `@types/chrome`  | Upgrade to 4.1.19, or install `@types/chrome`          |
| `Cannot find namespace 'chrome'`          | Same cause, in a type position                        | Upgrade to 4.1.19, or install `@types/chrome`          |
| `Cannot find module './styles.css'`       | `extension-env.d.ts` is out of `include`              | Add the file to `include`                              |
| `Cannot find name 'browser'`              | The project never ran `dev` or `build`                | Run either command once to generate types              |
| A name such as `chrome.tabs.TabChangeInfo` is missing after an upgrade | The project moved from `@types/chrome` to `chrome-types` | Install `@types/chrome`, then run `dev` or `build` once |
| Type errors in a committed `extension-env.d.ts` in CI | `tsc` ran before the CLI rewrote the file | Run `dev`, `build`, or `start` before `tsc` |

## Best practices

- Treat `extension-env.d.ts` as build output. Commit it if you like, but never edit it.
- Declare a type package in your own `devDependencies` only when you need a specific version of it, or to keep `@types/chrome`.
- Run `tsc --noEmit` in continuous integration. The Extension.js build does not fail on type errors.
- Run `extension build` before `tsc` in continuous integration. `dev`, `build`, and `start` regenerate `extension-env.d.ts`, and `tsc` does not.
