This page is part of the Extension.js documentation. Extension.js builds and runs browser extensions from one `manifest.json` for Chrome, Edge, Firefox, and Safari, and stops at the package that `extension build --zip` produces, so the values below feed your own submission tooling.

Automated Chrome Web Store submissions need two identifiers and one credential set:

| Value                | What it looks like                                                   | Where it comes from                                                  |
| -------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Extension ID         | 32 lowercase letters, for example `abcdefghijklmnopabcdefghijklmnop` | The Developer Dashboard item URL, after the first manual upload      |
| Publisher ID         | A UUID, for example `f1e2d3c4-0000-4000-8000-a1b2c3d4e5f6`           | **Publisher > Settings** in the Developer Dashboard                  |
| OAuth client ID      | Ends in `.apps.googleusercontent.com`                                | Google Cloud Console credentials page                                |
| OAuth client secret  | Starts with `GOCSPX-`                                                | Generated with the client ID                                         |
| OAuth refresh token  | Starts with `1//`                                                    | Minted against the client ID, see below                              |
| Service account JSON | A JSON key file                                                      | Google Cloud Console, alternative to the OAuth trio                  |

You need either the OAuth trio or the service account, not both. When both are configured, the service account wins.

<Note>
  [extension.dev](https://docs.extension.dev),
  the sponsor of Extension.js, handles publishing, store submission, and sharing
  from the same project. Its docs cover the steps after `extension build`.
</Note>

## Prerequisites

<Warning>
  The Chrome Web Store API cannot create a new item. The first upload of a new
  extension must happen by hand in the Developer Dashboard. The 32-character
  extension ID only exists after that upload.
</Warning>

1. Register a developer account at the
   [Chrome Web Store Developer Dashboard](https://chrome.google.com/webstore/devconsole).
   Registration has a one-time $5 fee.
2. Turn on 2-step verification for your Google Account. Google requires it
   to publish or update an extension.
3. Build a store zip (`npx extension build --browser chrome --zip`).
4. Upload that zip manually in the dashboard to create the item.
5. Copy the extension ID from the item's dashboard URL.
6. Copy the publisher ID from **Publisher > Settings** in the Developer
   Dashboard. If you belong to more than one publisher, switch to the right
   one first. The same UUID is in your dev console URL,
   `chrome.google.com/webstore/devconsole/<UUID>`.

Extension.js does not submit to a store, so it never asks you for these
values. This page is the manual path: create the OAuth client yourself and
mint the refresh token yourself.

<Note>
  Two routes mint the refresh token, and each one needs its own client type. A
  Web application client goes with the Google OAuth Playground. A Desktop app
  client goes with a loopback consent flow. The error `redirect_uri_mismatch`
  means that the client type and the minting route were mixed.
</Note>

## Create the OAuth client

1. Create or choose a project in the
   [Google Cloud Console](https://console.cloud.google.com).
2. Enable the
   [Chrome Web Store API](https://console.cloud.google.com/apis/library/chromewebstore.googleapis.com)
   for that project.

Then choose one of the two routes below. A service account skips both, and a
later section covers it.

### Route 1: a Web application client and the OAuth Playground

This is the route in Google's guide,
[Use the Chrome Web Store API](https://developer.chrome.com/docs/webstore/using-api).

1. On the [credentials page](https://console.cloud.google.com/apis/credentials),
   create an OAuth client ID with application type **Web application**.
2. Add `https://developers.google.com/oauthplayground` to the
   **Authorized redirect URIs**.
3. Copy the client ID and the client secret.
4. Open the [OAuth 2.0 Playground](https://developers.google.com/oauthplayground).
5. Open the settings and choose **Use your own OAuth credentials**.
6. Enter your client ID and client secret.
7. Enter `https://www.googleapis.com/auth/chromewebstore` in
   **Input your own scopes**.
8. Click **Authorize APIs**.
9. Sign in with the Google Account that owns the store items.
10. Click **Exchange authorization code for tokens**.
11. Copy the refresh token.

### Route 2: a Desktop app client and a loopback flow

1. On the [credentials page](https://console.cloud.google.com/apis/credentials),
   create an OAuth client ID with application type **Desktop app**.
2. Copy the client ID and the client secret.
3. Mint a refresh token for that client with a loopback consent flow on
   `127.0.0.1`, which is the redirect a Desktop app client accepts. The token
   must authorize the `https://www.googleapis.com/auth/chromewebstore` scope.

`redirect_uri_mismatch` has two causes. A Desktop app client was taken to the
Playground, or a Web application client lacks the Playground redirect URI.

<Warning>
  If your OAuth consent screen is in **Testing** status, Google revokes the
  refresh token after 7 days. Your first submission works and the credential
  dies a week later. Publish the consent screen (In production), or use a
  service account, which has no such expiry.
</Warning>

## Alternative: a service account

A Google Cloud service account avoids OAuth consent entirely and is the most
stable choice for CI:

1. In the Google Cloud Console, create a service account in the same project
   that has the Chrome Web Store API enabled.
2. Create a JSON key for it and download the file.
3. In the Chrome Web Store dev console, open **Account** and add the service
   account's email address to your publisher. One service account per
   publisher.

Provide the JSON key content (or a path to the file) as the credential. When
a service account is configured, it is preferred over the OAuth trio.

## Blast radius and rotation

<Warning>
  Chrome credentials are publisher-wide, not per extension. A token that can
  publish one item can publish every item under the same publisher account.
  Treat the refresh token and the service account key accordingly, and prefer a
  separate publisher account per client if you manage extensions for others.
</Warning>

To rotate, mint a new refresh token, or a new service account key, and re-enter
it wherever it is stored.

## Name map

The environment variable each value answers to:

| Value                | Env var                       |
| -------------------- | ----------------------------- |
| OAuth client ID      | `CHROME_CLIENT_ID`            |
| OAuth client secret  | `CHROME_CLIENT_SECRET`        |
| Refresh token        | `CHROME_REFRESH_TOKEN`        |
| Service account JSON | `CHROME_SERVICE_ACCOUNT_JSON` |
| Extension ID         | `CHROME_EXTENSION_ID`         |
| Publisher ID         | `CHROME_PUBLISHER_ID`         |

## Listing metadata stays manual

The Chrome Web Store API accepts no listing metadata. Store listing copy,
screenshots, and permission justifications are entered in the Developer
Dashboard by hand. Keep them in the Chrome section of
[STORE.md](/docs/workflows/store-metadata) so every resubmission copies from
one tracked source.
