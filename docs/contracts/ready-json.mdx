Poll one JSON file to know when a session is ready, broken, or gone.

Every `dev`, `start`, `preview`, and `build` run writes `dist/extension-js/<browser>/ready.json` atomically on each compile. The current contract is `schemaVersion: 2`.

From the release after 4.2.0, a Safari `build` writes `status: "ready"` only after the app is packaged. A packaging failure marks the contract `error` with `code: "build_failed"`.

A `preview` with no build loads the source folder and still writes its contract to the project's `dist/extension-js/<browser>/ready.json`, with every browser field a built preview carries.

## Statuses

| Status     | Meaning                                                                       |
| ---------- | ----------------------------------------------------------------------------- |
| `starting` | The run began. The file resets, and `events.ndjson` is truncated for the run. |
| `ready`    | The latest compile succeeded and the output is on disk. From the release after 4.1.41, under `dev` with a browser to launch, the launcher has also stamped its fields. See [Two-phase readiness](#two-phase-readiness). |
| `error`    | The compile failed, the browser never started or exited before the extension loaded, or the browser refused or lost the extension. |
| `stopped`  | The watch closed. Stamped with `code: "shutdown"` so a dead session can never advertise `ready`. |

## Two-phase readiness

`status: "ready"` means compiled. The browser may still be launching, except under `dev` as described next, and the service worker may not be connected yet.

From the release after 4.1.41, under `dev` with a browser to launch, `status` stays `starting` after the compile and turns `ready` once the launcher has stamped `browserPid`, `binary`, `profilePath` and the debugger port (`cdpPort` on Chromium, `rdpPort` on Firefox). `executorAttachedAt` can follow `ready` unless the session was started with `--allow-control` or `--allow-eval`, where `ready` waits for it up to 10 seconds.

The `ready` line on stdout is a stricter claim in a Chromium `dev` session: the launcher prints it only once the runtime inside the extension has connected (`executorAttachedAt`). When the browser is up and nothing connects within 15 s, the launcher prints what it is waiting on instead, stamps `browserUpNotAttachedAt` with a hint, and prints `ready` the moment the attach lands.

Act tooling (`eval`, `storage`, `reload`, `open`, `inspect`) needs the second phase. Wait until the contract carries `runtime: "attached"` and an `executorAttachedAt` timestamp before you drive the extension.

The attach stamp is idempotent and survives recompiles. An attach also clears any earlier `extension_load_refused` state, because the executor runs inside the guest.

### Sessions that take act verbs hold ready

From the release after 4.1.39, a session that takes act verbs keeps `status: "starting"` until the extension's background connects or 10 seconds pass. This applies to:

- `preview` and `start` with `--allow-control` or `--allow-eval`. A build with no background does not wait, because nothing connects from it.
- `dev` with `--allow-control` or `--allow-eval` and a browser that the session launches.

While `dev` waits, the contract carries `awaitingExecutorSince`. The field goes away when the background connects or the wait runs out.

The wait is bounded, so `ready` still arrives for an extension that never connects, with no `executorAttachedAt` beside it. `executorAttachedAt` stays the field that says an act verb can run.

On Firefox, a `dev` session that waits needs both the RDP port and the background before it reports `ready`.

## Field reference (schema v2)

Fields that are always present:

| Field              | Type             | Meaning                                                                  |
| ------------------ | ---------------- | ------------------------------------------------------------------------ |
| `schemaVersion`    | `2`              | The ready contract's own version.                                        |
| `schema`           | `1`              | Advertises that this engine speaks the schema-1 [result envelope](/docs/contracts/result-envelope). |
| `status`           | string           | `starting`, `ready`, `error`, or `stopped`.                              |
| `command`          | string           | `dev`, `start`, `preview`, or `build`.                                   |
| `browser`          | string           | The browser target that this session serves.                             |
| `runId`            | string           | The session identity. Join key across `ready.json`, `events.ndjson`, and `logs.ndjson`. |
| `startedAt`        | ISO string       | When the run began.                                                      |
| `distPath`         | string           | Absolute path to the compiled extension.                                 |
| `manifestPath`     | string           | Absolute path to the source manifest.                                    |
| `port`             | number or null   | The port that the dev server actually bound.                             |
| `pid`              | number           | The dev server process id. Check liveness before trusting the contract.  |
| `pidStartedAt`     | ISO string       | From 4.1.40, when the process behind `pid` started. A reused pid has another start time, so compare both. |
| `pidStartId`       | string           | From the release after 4.2.0, Linux only: the boot id and the kernel start tick of `pid`, joined by a colon. A clock step, as in a resumed VM or WSL2, moves `pidStartedAt` but never this value. When you can read it for the live pid, compare it for equality instead of the dates. Absent on other systems. |
| `ts`               | ISO string       | When this document was last written. From the release after 4.2.0, when `status` was last written: a fact stamped beside the status does not move it. |
| `compiledAt`       | string or null   | When the latest successful compile finished.                             |
| `errors`           | string[]         | ANSI-stripped compile errors, capped at 10 entries.                      |
| `toolchainVersion` | string           | The Extension.js version that produced this tree.                        |

Fields that appear when known:

| Field              | Type     | Meaning                                                                          |
| ------------------ | -------- | -------------------------------------------------------------------------------- |
| `host`             | string   | The dev server host.                                                             |
| `code`             | string   | Machine name for the error state, see below.                                     |
| `message`          | string   | Human sentence beside `code`.                                                    |
| `instanceId`       | string   | The dev instance identity for multi-instance setups.                             |
| `instanceExplicit` | boolean  | Whether the instance id was user-supplied.                                       |
| `controlPort`      | number or null | The control bridge WebSocket port.                                         |
| `controlPath`      | string   | The control bridge WebSocket path (`/extjs-control`).                            |
| `controlPortUnavailableReason` | string | Why `controlPort` is null when the session asked for a control channel. |
| `logsPath`         | string   | Relative path to `logs.ndjson`.                                                  |
| `cdpPort`          | number   | Chromium launches: the CDP port, stamped post-launch. From the release after 4.1.41, sessions started at the same time each get their own debugging port, so read this field instead of assuming 9222. On `preview` and `start`, it is on the record when the card prints. |
| `rdpPort`          | number   | Gecko launches: the RDP debugger-server port, stamped post-launch. From the release after 4.1.41, sessions started at the same time each get their own port, so read this field. |
| `rdpPortError`     | string   | Gecko launches, from 4.1.39: why Firefox opened no remote debugging port. `rdpPort` is absent beside it. |
| `webdriverPort`    | number   | Safari `dev` sessions: the port of the safaridriver session the launcher holds beside the app. Safari grants one automation session at a time, so attach to this one instead of opening your own. |
| `webdriverSessionId` | string | The session id beside `webdriverPort`.                                           |
| `webdriverUnavailableReason` | string | Why the launcher holds no WebDriver session, such as Safari's Allow Remote Automation being off, or another Safari being open when the session was asked for. |
| `webdriverRequestPath` | string | Safari `dev` sessions: a file a client touches to ask the launcher for a fresh WebDriver session. |
| `safari`           | object   | Safari `dev` sessions: how far the enable step got and why it stopped, so nobody parses the session log. `bundleId`, `extensionId` and `team` name the appex Safari files, `switchId` the row in Safari Settings, `enableAttempted` whether `--enable-extension` ran, `step` the last step reached (`not-asked`, `accessibility`, `safari`, `unsigned`, `pluginkit`, `enabled`, `websites`, `done`), `enabled`, `listed` and `otherWebsites` what the switches read, `reason` the sentence the step stopped on, and `earlierExtensionIds` the ids macOS still lists from earlier builds of this project, whose switches do not carry over. |
| `cdpFaultCode`     | string   | Chromium `dev` sessions: stamped when the CDP wire failed after the browser came up, with one of the debug protocol warning codes such as `W_CDP_TIMEOUT` or `W_CDP_NOT_CONNECTED`. Releases up to 4.1.41 stamped the `E_*` name. The session stays `ready` because the browser is up, but reload and HMR cannot attach until the fault is fixed. Preserved across recompiles of the same run. |
| `cdpFaultMessage`  | string   | The plain line beside `cdpFaultCode`. The `ready` frame under `--output json` carries the same fault on `warnings` as `W_CDP_...: message`. |
| `browserUpNotAttachedAt` | ISO string | Chromium `dev` sessions: stamped when the browser process is up and the extension compiled, but the runtime inside the extension has not connected to the control bridge within the launcher's grace period (15 s). The status stays `ready`, and the `ready` line on stdout is held back until the attach. Cleared by the first attach. |
| `browserUpNotAttachedWaitMs` | number | How long the launcher waited before stamping `browserUpNotAttachedAt`. |
| `browserUpNotAttachedHint` | string | The plain sentences beside it: the browser and its pid, the profile path, whether that profile had been run before, and the fresh-profile way out. |
| `profileReused` | boolean | Chromium launches: whether a browser had already run with the profile directory before this launch. A reused profile is the usual reason a browser comes up with nothing attached. |
| `profilePath`      | string   | The resolved profile directory. Ephemeral profile names are generated, so read them here. |
| `binary`           | string   | Absolute path to the browser binary this session actually launched. Stamped for every run, including the ones that did not name a binary: those are the runs where the resolver chose for you and the path is not otherwise visible. |
| `binaryProvenance` | string   | How that binary was chosen: `managed` (the Extension.js cache), `pinned` (a binary flag or a binary variable), `system` (an installed browser), or `snapshot` (a cached dev-channel build). |
| `binaryPinnedBy`   | string   | From the release after 4.1.39, the flag or variable that named a `pinned` binary, such as `--chromium-binary` or `FIREFOX_BINARY`. Absent for every other provenance. |
| `browserPid`       | number   | The browser process id. The supported handle for tearing the browser down.       |
| `browserStartedAt` | ISO string | From 4.1.40, when the process behind `browserPid` started, so a reused pid is caught. Absent when the process table cannot date it. |
| `browserStartId`   | string   | From the release after 4.2.0, Linux only: the boot id and the kernel start tick of `browserPid`, joined by a colon, as in `pidStartId`. A clock step never moves it, so compare it for equality to tell a reused pid. Absent when the process table cannot be read. |
| `launcherPid`      | number   | From 4.1.22, the process that the launcher spawned, kept when the browser hands its session to another process. `browserPid` names the live one. |
| `launcherStartedAt` | ISO string | From 4.1.40, when the process behind `launcherPid` started. |
| `launcherStartId`  | string   | From the release after 4.2.0, Linux only: the same value for `launcherPid`. |
| `extensionId`      | string   | The id that the browser serves the dist under. Browser-confirmed when available, derived otherwise. From the release after 4.1.41, the field is absent while the contract records a load refusal, unless the browser itself confirmed the id. |
| `extensionIdSource` | string  | From 4.1.35, where `extensionId` came from: `browser`, `derived`, or `packager`. |
| `extensionBaseUrl` | string   | Firefox launches, from the release after 4.1.39: the `moz-extension://<uuid>/` address that the browser serves the extension from. Firefox chooses the UUID per profile, so the add-on id does not reveal it. |
| `devAdditions`     | array    | `dev` sessions, from the release after 4.1.39: what the session has that the production build lacks. See [Dev additions](#dev-additions). |
| `extensionName`    | string   | The extension's name, as build provenance.                                       |
| `extensionVersion` | string   | The extension's version, as build provenance.                                    |
| `browserExitedAt`  | ISO string | Stamped when the browser exits mid-session without being asked. Preserved across recompiles. |
| `browserExitCode`  | number or null | The exit code beside `browserExitedAt`.                                    |
| `browserExitSignal` | string or null | The signal beside `browserExitedAt` when the browser died of one, such as `SIGTRAP` for a crash. A crash carries no exit code, so this is the one clue about why it went. |
| `browserLaunchFailedAt` | ISO string | Stamped when no browser process came up at all. Preserved across recompiles. |
| `browserLaunchFailedReason` | string | The reason beside `browserLaunchFailedAt` as one plain line, such as the spawn error with the binary path. |
| `extensionLoadRefusedAt` | ISO string | Stamped when the browser refused to load the extension. From the release after 4.1.41, a stopped contract keeps it. |
| `extensionLoadRefusedReason` | string | The browser's reason beside `extensionLoadRefusedAt`. From the release after 4.1.41, a stopped contract keeps it. |
| `extensionLoadRefusedCause` | string | From the release after 4.1.41. Present when the launcher knows from the manifest why the browser refused and the browser's words do not say it. Kept on a stopped contract, and cleared with the refusal. |
| `runtime`          | `"attached"` or `"detached"` | `attached` once the service worker has connected and can be driven. From 4.1.20, `detached` once the last connected extension context disconnects, and `attached` again on reconnect. |
| `executorAttachedAt` | ISO string | When the service worker first connected. Kept as provenance after a detach.  |
| `executorDetachedAt` | ISO string | From 4.1.20, when the last connected extension context disconnected.          |
| `awaitingExecutorSince` | ISO string | `dev` sessions, from the release after 4.1.39: when the session began to hold `ready` for the background. Removed once the background connects or 10 seconds pass. |
| `managedExtensions` | array   | Every extension that the engine loads besides yours, as `{path, id?}` records. Subtract them by id in a census. |
| `reloadedAt`       | ISO string | `dev` sessions, from 4.1.34: when the last reload after a compile was applied. The reload of a compile is live once `reloadedAt` is later than its `compiledAt`. A compile that reloads nothing leaves the stamp as it was. |
| `reloadKind`       | string   | The kind of that reload: `full`, `background`, `content`, `page`, or `safari-resync`. |
| `reloadLabel`      | string   | A short label for that reload, when it has one.                                  |
| `endedAsFailedAt`  | ISO string | From 4.2.0, stamped when the session ended as a failure. The status reads `error` from then on. |
| `endedAsFailedCode` | string  | From 4.2.0, the `E_*` code that ended the session, such as `E_CONFIG_LOAD`. `--wait` answers with this code before the one that `code` maps to. |

## Dev additions

From the release after 4.1.39, a `dev` contract lists what the session has that a production build of the same source lacks. Each `devAdditions` entry carries a `kind`, a `value`, and a `reason`:

| `kind`                    | `value`                                                    | Extra fields                                                     |
| ------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------- |
| `permission`              | A permission that the dev manifest adds, such as `scripting`. | none                                                          |
| `host_permission`         | A host pattern that the dev manifest adds.                 | none                                                             |
| `web_accessible_resource` | A resource that the dev manifest exposes, such as `hot/*`. | `matches`, the origins that can read it. Absent on Manifest V2.  |
| `manifest_change`         | Another dev-only manifest change, such as `background.persistent true` or `externally_connectable.ids *`. | none |
| `browser_flag`            | A launch flag that changes what you see in the browser.    | `applied`, `cause`, and `change`.                                |
| `browser_preference`      | A browser preference that the session writes to a kept profile, as `name=value`. | `applied`, `cause`, and `change`. |

The first four kinds are the difference between your manifest and the dev manifest. From the release after 4.1.41, `manifest_change` reports the other dev-only changes. These are a looser pages policy, a reopened `externally_connectable` list, an added background, and a background kept alive. Each recompile replaces them. The launcher writes the `browser_flag` and `browser_preference` entries, and a recompile keeps them.

A `browser_flag` entry says whether this launch passes the flag (`applied`) and what decided that (`cause`). `cause` is `default`, `browser-flags`, `debugger-permission`, or `exclude-browser-flags`. `change` names the one edit that flips the verdict.

A `browser_preference` entry appears on Chromium when the profile outlives the session, as with `--profile <path>`. The session sets `session.restore_on_startup` to `5`, so Chrome opens a new tab and does not restore the pages of the previous run. The value stays in that profile after the session ends. Its `cause` is `default`, `preferences` when your config sets the preference, or `unavailable` when the browser refused the write. See [Browser preferences](/docs/browsers/browser-preferences#the-startup-preference-on-a-kept-profile).

```json
{
  "devAdditions": [
    {
      "kind": "permission",
      "value": "scripting",
      "reason": "the dev reload registers content scripts and injects the rebuilt files into open tabs"
    },
    {
      "kind": "web_accessible_resource",
      "value": "hot/*",
      "matches": ["https://example.com/*"],
      "reason": "a content script fetches its hot update chunks from the page"
    },
    {
      "kind": "browser_flag",
      "value": "--silent-debugger-extension-api",
      "applied": false,
      "cause": "debugger-permission",
      "reason": "the manifest declares \"debugger\", so the debugging bar and its Cancel button show as they do for a user",
      "change": "list the flag under browserFlags in extension.config.js to hide the bar"
    }
  ]
}
```

The identity card prints the same entries as `Dev only` and `Dev flag` lines. See [Reading CLI output](/docs/concepts/reading-cli-output#lines-under-the-card). Two flags follow the `debugger` permission. See [Browser flags](/docs/browsers/browser-flags#the-debugger-permission-changes-two-flags).

## Error states

The `code` field names the failure class. Four codes matter for automation:

| `code`                    | What happened                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| `extension_load_refused`  | The session runs, but the browser threw the extension out. Every other surface looks healthy, only the contract says so. From the release after 4.1.41, the act commands (`eval`, `storage`, `reload`, `inspect`, `navigate`) answer `E_EXTENSION_LOAD_REFUSED` with the browser's reason, and `doctor` names it on the `ready-contract` row. Carries `extensionLoadRefusedAt` and `extensionLoadRefusedReason`. From the release after 4.1.41, it also carries `extensionLoadRefusedCause` when the launcher knows one. |
| `profile_locked`          | Another live session holds the profile, so the browser never started. Carries `profileLockedAt` and a `profileLockOwner` with `host` and `pid`. |
| `browser_exited`          | The browser process died. `start` and `preview` flip to `error`. `dev` flips to `error` only when the browser exits before the extension loaded. After that point `dev` keeps its compile status and only stamps `browserExitedAt`. A Firefox that exits before its debugger answers lands here within about a second. |
| `browser_launch_failed`   | No browser process came up: the binary is missing, cannot be executed, or the pin is wrong. A Firefox that runs but whose debugger never answers lands here too, and Extension.js stops that process. `dev`, `start`, and `preview` all flip to `error`. Carries `browserLaunchFailedAt` and `browserLaunchFailedReason`. A launch refused for a bad `--chromium-binary` or `--gecko-binary` pin also carries `browserLaunchFailedCode: "E_BROWSER_BINARY_INVALID"`. A Gecko launch refused in system profile mode carries `browserLaunchFailedCode: "E_FLAG_NOT_SUPPORTED_HERE"`. |

From 4.2.0, a `build` that is refused before it compiles, such as by an invalid [`perfBudgets`](/docs/workflows/performance-playbook#invalid-budget-values) value, marks the existing `ready.json` with `status: "error"` and `code: "build_failed"`. The refusal's own code goes in `endedAsFailedCode`. A project that never built gets no file, and the file of a live `dev` session is left alone.

A load refusal outlives the next successful compile. Only a new run (`starting`) or a real executor attach clears it. From the release after 4.1.41, a stopped contract keeps `extensionLoadRefusedAt`, `extensionLoadRefusedReason`, and the cause.

A `dev` session whose browser exited before the extension loaded stays in `error` across recompiles, because a recompile does not bring the browser back. A launch failure outlives recompiles too, until a browser does start or a new run begins.

From the release after 4.2.0, every field that the launcher stamps is kept across recompiles of the same run. A browser verdict (`browser_exited`, `browser_launch_failed`, `profile_locked`, or `extension_load_refused`) keeps `status: "error"`, its `code`, and its `message` after a compile that succeeds. Only `compile_error` and `compile_failed` clear on the next good compile.

## Waiting with --wait

`extension dev --wait` and `extension start --wait` poll the contract every 250 ms and exit when it reports `ready`. Pair them with `--output json` for a machine result.

The wait loop refuses to trust stale files. Three checks run on every read:

1. The `command` field must match the waiting command.
2. The `pid` must be alive. For `dev`, a dead producer always means stale, so polling continues.
3. For `start`, a dead pid is accepted only when the contract is fresh. Freshness means `ts`, `compiledAt`, or `startedAt` is within the last 60 seconds.

A timeout exits with `E_READY_TIMEOUT`. A contract in `error` status fails the wait with its message, and the `error.code` of the result resolves the contract's own code:

| Contract `code`           | `--wait` error code        |
| ------------------------- | -------------------------- |
| `compile_error`           | `E_COMPILE`                |
| `compile_failed`          | `E_COMPILE_FATAL`          |
| `build_failed`            | `E_COMPILE`                |
| `dev_server_start_failed` | `E_DEV_SERVER_START`       |
| `browser_launch_failed`   | `E_BROWSER_LAUNCH`         |
| `browser_exited`          | `E_BROWSER_EXITED`         |
| `profile_locked`          | `E_PROFILE_LOCKED`         |
| `extension_load_refused`  | `E_EXTENSION_LOAD_REFUSED` |
| A code outside this list  | `E_READY_ERROR_STATUS`     |

From 4.2.0, a contract that carries `endedAsFailedCode` fails the wait with that code first.

A `browser_launch_failed` contract that carries `browserLaunchFailedCode: "E_BROWSER_BINARY_INVALID"` or `"E_FLAG_NOT_SUPPORTED_HERE"` fails the wait with that code and `status: "usage"` instead of `E_BROWSER_LAUNCH`.

From the release after 4.1.41, a `--wait` on a run that ended on a refusal answers `E_EXTENSION_LOAD_REFUSED` at once and does not wait for `E_READY_TIMEOUT`, unless the manifest changed after the refusal.

## Joining the session files

The same directory holds `events.ndjson` (compile timeline) and `logs.ndjson` (extension console output). Every row in both carries the `runId` from `ready.json`.

`events.ndjson` is truncated at every run start, so it only ever describes the current run. Event types are `compile_start`, `compile_success`, `compile_error`, `browser_exited`, `browser_launch_failed`, and `shutdown`. From the release after 4.2.0, a `restart_failed` row records a `dev` restart that could not be made, such as a config or entry change whose next compiler or server failed. It carries the error `code`, the `reason`, and `serving`: `true` when the build from before the restart still serves the session and retries on the next change, `false` when no server is left and the session ends. A `browser_exited` row mirrors the launcher's exit stamp, with `exitCode`, `exitSignal`, and `browserExitedAt`, so the timeline says when and how the browser went. After it, every act verb answers `E_CONTROL_UNAVAILABLE` naming the exit and the restart, since no service worker reconnects until a new `dev` session relaunches the browser. A `browser_launch_failed` row mirrors the launch failure stamp, with `browserLaunchFailedAt` and `reason`.

From the release after 4.2.0, a `warning` row records something the session warned about between two compiles, such as a reload that the extension never confirmed. It carries the warning `code` and the `reason`, and it is written in text mode as well.
