Follow a live session as one JSON frame per transition.

A terminating envelope cannot describe a session, so `dev`, `start`, and `preview` stream one schema-1 frame per lifecycle transition. Each frame is a complete [result envelope](/docs/contracts/result-envelope) on its own line.

## Turning the stream on

The stream keys off the `EXTENSION_OUTPUT` environment variable. Set it to `json` or `ndjson` and frames own stdout:

```bash
EXTENSION_OUTPUT=ndjson npx extension@latest dev ./my-extension --browser chromium --no-browser
```

While the stream is on, human copy that shares stdout moves to stderr. Error copy always stays on stderr, machine mode never hides a failure.

## Frame statuses

| Status           | `ok`  | When it arrives                                                            |
| ---------------- | ----- | -------------------------------------------------------------------------- |
| `starting`       | true  | Once, when the session begins, after the config loads and the compiler exists. Carries `requestedPort` and the bound `port`. |
| `compiled`       | true  | The first successful compile. Carries `assets` and `durationMs`.            |
| `recompiled`     | true  | Every later successful compile.                                             |
| `compile-failed` | false | A compile finished with errors, first or later.                             |
| `ready`          | true  | Once, when `ready.json` is on disk for this session.                        |
| `browser-exited` | false | The browser died mid-session, see below.                                    |
| `restart-failed` | false | From the release after 4.1.41. A restart could not build the next bundle, so the previous build keeps serving and `value.serving` is `true`. `error.code` is the failure's own code, or `E_DEV_SERVER_START`. Save the changed file again to retry. |
| `load-refused`   | false | The browser refused the extension. The session goes on and offers it again on the next compile. |
| `ready-failed`   | false | From the release after 4.1.41. `ready.json` reports `error` while the session goes on, for example a failed launch. The next compile tries again. |
| `failed`         | false | A session-level failure that ends the run, for example the server never bound, or the next server of a restart could not start. |
| `stopped`        | varies | The last frame. `ok: true` when the session ended by itself with exit code `0`. `ok: false` with `E_INTERRUPTED` and `value.signal` when a signal such as `SIGINT` stopped it. |

Every frame's `value` carries the session identity: `command`, `browser`, `distPath`, `pid`, `port`, plus `readyPath`, `eventsPath`, `runId`, `instanceId`, and `toolchainVersion` when known.

A run refused before the session begins sends one `failed` frame and no `starting` frame. A missing manifest, a config file that fails to load, and a remote URL with no usable archive all end that way.

## Compile failures

A `compile-failed` frame carries the compiler output inside `value.output`, so you never scrape stdout. The output is ANSI-stripped and capped at 2000 characters. When the cap cuts it, the frame sets `truncated: true`.

The first failure of a session uses code `E_FIRST_COMPILE`, every later one uses `E_COMPILE`.

The frame also carries `error.details`, one entry per diagnostic with its own code, file, and position, errors first, in the shape the [result envelope](/docs/contracts/result-envelope) describes under Compile diagnostics. The list is capped at 20 entries, and `truncated: true` is set when either the output or the list was cut.

{"schema":1,"ok":true,"command":"dev","status":"starting","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"requestedPort":8080},"error":null,"warnings":[]}
{"schema":1,"ok":true,"command":"dev","status":"compiled","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4","assets":12,"durationMs":841},"error":null,"warnings":[]}

## Ready follows the contract

The `ready` frame reads `ready.json` before it fires. A compile can succeed while the browser refuses the extension, and the contract stays in `error` when that happens.

In that case the stream emits a `ready-failed` frame while the session goes on, or a `failed` frame when the run ends. Its code is `E_READY_ERROR_STATUS`, and `value.readyCode` names the contract's own error code.

The same frame arrives when the browser never started or exited before the extension loaded. `value.readyCode` is then `browser_launch_failed` or `browser_exited`. A Firefox whose debugger never answers counts as a launch failure.

A bad `--chromium-binary` or `--gecko-binary` pin also reports `readyCode: "browser_launch_failed"`, but its frame has `status: "usage"` and `error.code: "E_BROWSER_BINARY_INVALID"`, the code every command gives that pin.

A Chromium `dev` session whose CDP wire failed after the browser came up still sends `ready`, because the browser is up. That frame carries the fault on `warnings` as `W_CDP_...: message`, the same pair the contract stamps as `cdpFaultCode` and `cdpFaultMessage`, see [ready.json](/docs/contracts/ready-json). Reload and HMR cannot attach until the fault is fixed.

## Browser exits

A background watcher polls `ready.json` once per second for the launcher's exit stamp. When `browserExitedAt` appears, the stream emits one `browser-exited` frame.

The frame's code depends on the evidence in the contract:

- `E_PROFILE_LOCKED` when the contract shows a locked profile. The browser never started, another session holds the profile.
- `E_BROWSER_LAUNCH` for every other unexpected exit.

The frame's `value` carries `exitCode`, `exitSignal`, and `browserExitedAt` when the contract has them. A crash has no exit code, only a signal such as `SIGTRAP`.

## Restarts and shutdown

From the release after 4.1.41, a restart whose next bundle cannot be built sends one `restart-failed` frame, and the old server keeps serving. If the next server cannot start after the old one stopped, the stream sends `failed` and the process exits `1`.

A shutdown has 10 seconds to finish, then the process exits `1`. A second `Ctrl+C` more than one second after the first one also forces exit `1` at once. A forced shutdown never reports success.
