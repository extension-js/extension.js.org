本页属于 Extension.js 文档。Extension.js 从一个 `manifest.json` 出发，为 Chrome、Edge、Firefox 和 Safari 构建并运行浏览器扩展，并在 `extension build --zip` 产出的安装包处止步，因此下面这些值是给你自己的提交工具用的。

自动化提交到 Chrome Web Store 需要两个标识符和一组凭据：

| 值                   | 长什么样                                                     | 从哪里来                                                              |
| -------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------- |
| Extension ID         | 32 个小写字母，例如 `abcdefghijklmnopabcdefghijklmnop`       | 第一次手动上传之后，开发者后台里该商品的 URL                          |
| Publisher ID         | 一个 UUID，例如 `f1e2d3c4-0000-4000-8000-a1b2c3d4e5f6`       | 开发者后台里的 **Publisher > Settings**                               |
| OAuth client ID      | 以 `.apps.googleusercontent.com` 结尾                        | Google Cloud Console 的凭据页面                                       |
| OAuth client secret  | 以 `GOCSPX-` 开头                                            | 与 client ID 一起生成                                                 |
| OAuth refresh token  | 以 `1//` 开头                                                | 针对该 client ID 生成，见下文                                         |
| Service account JSON | 一个 JSON 密钥文件                                           | Google Cloud Console，OAuth 三件套的替代方案                          |

你只需要 OAuth 三件套或服务账号其中之一，不需要两者都配。两者都配置时，服务账号优先。

<Note>
  [extension.dev](https://docs.extension.dev) 是 Extension.js 的赞助方，可以在同一个项目里完成发布、商店提交和分享。它的文档覆盖 `extension build` 之后的步骤。
</Note>

## 前置条件

<Warning>
  Chrome Web Store API 无法创建新商品。一个新扩展的第一次上传必须在开发者后台
  （Developer Dashboard）里手动完成。那 32 个字符的 extension ID 只有在那次上传
  之后才存在。
</Warning>

1. 在 [Chrome Web Store 开发者后台](https://chrome.google.com/webstore/devconsole)
   注册一个开发者账号。注册需要一次性支付 5 美元。
2. 为你的 Google 账号开启两步验证。Google 要求开启它才能发布或更新扩展。
3. 构建一个商店 zip（`npx extension build --browser chrome --zip`）。
4. 在后台里手动上传这个 zip，以创建该商品。
5. 从商品的后台 URL 中复制 extension ID。
6. 在开发者后台的 **Publisher > Settings** 中复制 publisher ID。如果你属于
   多个发布者，请先切换到正确的那一个。同一个 UUID 也出现在你的开发者控制台
   URL `chrome.google.com/webstore/devconsole/<UUID>` 里。

Extension.js 不会替你提交到任何商店，因此它从来不会向你索要这些值。
本页讲的是手动路径：自己创建 OAuth 客户端，自己生成 refresh token。

<Note>
  生成 refresh token 有两条路线，每条路线需要各自的客户端类型。Web application
  类型的客户端搭配 Google OAuth Playground，Desktop app 类型的客户端搭配本地回环
  授权流程。`redirect_uri_mismatch` 错误说明客户端类型和生成路线混用了。
</Note>

## 创建 OAuth 客户端

1. 在 [Google Cloud Console](https://console.cloud.google.com) 中创建或选择一个项目。
2. 为该项目启用
   [Chrome Web Store API](https://console.cloud.google.com/apis/library/chromewebstore.googleapis.com)。

然后从下面两条路线中选一条。使用服务账号可以两条都跳过，后面有一节会讲到。

### 路线一：Web application 客户端加 OAuth Playground

这是 Google 的指南
[Use the Chrome Web Store API](https://developer.chrome.com/docs/webstore/using-api) 采用的路线。

1. 在[凭据页面](https://console.cloud.google.com/apis/credentials)创建一个
   OAuth client ID，应用类型选 **Web application**（Web 应用）。
2. 把 `https://developers.google.com/oauthplayground` 加入
   **Authorized redirect URIs**（已获授权的重定向 URI）。
3. 复制 client ID 和 client secret。
4. 打开 [OAuth 2.0 Playground](https://developers.google.com/oauthplayground)。
5. 打开设置，选择 **Use your own OAuth credentials**。
6. 填入你的 client ID 和 client secret。
7. 在 **Input your own scopes** 中填入
   `https://www.googleapis.com/auth/chromewebstore`。
8. 点击 **Authorize APIs**。
9. 用拥有这些商店商品的 Google 账号登录。
10. 点击 **Exchange authorization code for tokens**。
11. 复制 refresh token。

### 路线二：Desktop app 客户端加本地回环流程

1. 在[凭据页面](https://console.cloud.google.com/apis/credentials)创建一个
   OAuth client ID，应用类型选 **Desktop app**（桌面应用）。
2. 复制 client ID 和 client secret。
3. 用 `127.0.0.1` 上的本地回环授权流程为该客户端生成一个 refresh token，
   这正是 Desktop app 类型客户端所接受的重定向。该令牌必须获得
   `https://www.googleapis.com/auth/chromewebstore` 这个 scope 的授权。

`redirect_uri_mismatch` 有两种原因：把 Desktop app 客户端拿去了 Playground，
或者 Web application 客户端没有添加 Playground 的重定向 URI。

<Warning>
  如果你的 OAuth 同意屏幕还处于 **Testing**（测试）状态，Google 会在 7 天后
  吊销 refresh token。你的第一次提交能成功，而这份凭据一周后就失效了。请把同意
  屏幕发布出去（In production），或者改用服务账号，服务账号没有这种过期问题。
</Warning>

## 备选方案：服务账号

Google Cloud 的服务账号完全绕开了 OAuth 授权同意，是 CI 场景下最稳定的选择：

1. 在 Google Cloud Console 中，于那个已启用 Chrome Web Store API 的同一个项目里
   创建一个服务账号。
2. 为它创建一个 JSON 密钥并下载该文件。
3. 在 Chrome Web Store 开发者控制台中打开 **Account**（账号），把这个服务账号的
   邮箱地址添加到你的发布者账号下。一个发布者账号对应一个服务账号。

把 JSON 密钥的内容（或指向该文件的路径）作为凭据提供。配置了服务账号时，
它优先于 OAuth 三件套。

## 影响范围与轮换

<Warning>
  Chrome 凭据是发布者账号级别的，而不是按扩展划分的。一个能发布某个商品的令牌，
  也能发布同一个发布者账号下的每一个商品。请据此对待 refresh token 和服务账号
  密钥；如果你在为别人管理扩展，最好为每个客户使用一个独立的发布者账号。
</Warning>

要轮换凭据，就生成一个新的 refresh token 或新的服务账号密钥，并在存放它的地方
重新填入。

## 名称对照

每个值对应的环境变量：

| 值                   | 环境变量                      |
| -------------------- | ----------------------------- |
| OAuth client ID      | `CHROME_CLIENT_ID`            |
| OAuth client secret  | `CHROME_CLIENT_SECRET`        |
| Refresh token        | `CHROME_REFRESH_TOKEN`        |
| Service account JSON | `CHROME_SERVICE_ACCOUNT_JSON` |
| Extension ID         | `CHROME_EXTENSION_ID`         |
| Publisher ID         | `CHROME_PUBLISHER_ID`         |

## 商品页元数据仍然要手动填

Chrome Web Store API 不接受任何商品页元数据。商店文案、截图和权限说明都要在开发者
后台里手动填写。把它们放在 [STORE.md](/zh-Hans/docs/workflows/store-metadata) 的 Chrome
小节里，这样每次重新提交都从同一份纳入版本控制的来源复制。
