Extension.js 用 SWC 编译 TypeScript，它只擦除类型，从不检查类型。类型检查是你用 `tsc` 单独运行的一步。本页说明这一步如何解析 `chrome.*`、`browser.*` 和 `process.env`。

## Extension.js 会生成什么

当项目使用 TypeScript 时，`extension dev`、`extension build` 和 `extension start` 会在 `package.json` 旁边写下一个 `extension-env.d.ts` 文件。它在每次运行时都会被重新生成，所以不要编辑它。

这个文件会引入 `extension` 包发布的环境类型：

```ts extension-env.d.ts
/// <reference types="extension/types" />
/// <reference types="extension/types/polyfill" />
```

这些引用会给你：

| 引用                       | 它声明了什么                                                        |
| -------------------------- | ------------------------------------------------------------------- |
| `extension/types`          | `browser` 命名空间及其别名 `chrome`、`process.env` 与 `import.meta.env` 键 |
| `extension/types/polyfill` | `webextension-polyfill` 模块，供 `import browser from 'webextension-polyfill'` 使用 |
| 通配符模块                 | 对 `.css`、`.module.css`、`.png`、`.svg` 等资源的 `import`，以及 `?raw` 和 `?url` 导入 |

`EXTENSION_*` 环境变量键也在这里被赋予类型。这就是 `process.env.EXTENSION_MODE` 不需要额外配置就能解析的原因。

安装了 `@types/chrome` 的项目，第一条引用会不一样。本页的“保留 @types/chrome”一节展示了它。

当 `extension` 包无法从项目里解析时（例如只通过 `npx` 运行 CLI 的项目），这两条引用什么也找不到。这时生成的文件还会把通配符模块声明直接写在文件里，所以样式表、图片、`?raw` 和 `?url` 导入仍然能通过类型检查。

## 随 Extension.js 一起安装的类型

`extension` 包把这些引用需要的三个类型包列为依赖：

| 包                             | 它提供的类型            |
| ------------------------------ | ----------------------- |
| `chrome-types`                 | `browser.*` 命名空间及其别名 `chrome.*` |
| `@types/webextension-polyfill` | `webextension-polyfill` 模块 |
| `@types/node`                  | `process.env`           |

[`chrome-types`](https://www.npmjs.com/package/chrome-types) 是 Chrome 从 Chromium 源码生成的包。它的 `browser` 是原生命名空间，方法返回 Promise。`chrome` 是它的别名。

`chrome-types` 没有声明只有 Firefox 才有的 API。Firefox 的 `browser.sidebarAction` 和 `browser.browserAction` 由 Extension.js 自己提供类型。

它们会随 `extension` 一起安装，所以在一个新项目里，`tsc` 不需要额外安装就能解析 `chrome.*` 和 `browser.*`：

```bash
npx tsc --noEmit
```

构建并不需要这些包。SWC 从来不读类型，所以不管有没有它们，构建都会成功。

## 保留 @types/chrome

安装了 `@types/chrome` 的项目会继续使用它。`chrome` 的类型来自这个包，`browser` 的类型和以前一样来自 `webextension-polyfill`。

`@types/chrome` 和 `chrome-types` 都声明了 `chrome` 全局变量，所以这两个包不能同时加载。生成的 `extension-env.d.ts` 只引用其中一个。当你的 `package.json` 列出了 `@types/chrome` 时，它引用 `@types/chrome`。当项目目录或某个上级目录里存在 `node_modules/@types/chrome` 时，也是如此：

```ts extension-env.d.ts
/// <reference types="extension/types/legacy" />

// This project installs @types/chrome, so it types the extension APIs.
// Remove that package to get chrome-types and the native browser namespace.
/// <reference types="chrome" />

// Polyfill types for browser.* APIs
/// <reference types="extension/types/polyfill" />
```

改用 `chrome-types`：

1. 从项目里移除 `@types/chrome`。
2. 运行一次 `extension dev` 或 `extension build`。

回到 `@types/chrome`：

1. 把 `@types/chrome` 安装为开发依赖。
2. 运行一次 `extension dev` 或 `extension build`。

在默认配置下，`browser` 全局变量拥有原生类型。想要 `webextension-polyfill` 的类型，请导入这个模块：

```ts
import browser from "webextension-polyfill";
```

## 固定你自己的版本

`extension` 包接受 `@types/node` 和 `@types/webextension-polyfill` 的任意版本。它接受 `chrome-types` 0.1.460 或更高版本。当你的项目自己声明了其中一个时，npm、pnpm 和 Bun 会复用你的项目安装的那一份。

当你的 `tsconfig.json` 没有 `types` 数组时，TypeScript 也会加载你的项目声明的那一份。以你自己 `package.json` 里的版本为准：

```json package.json
{
  "devDependencies": {
    "@types/webextension-polyfill": "^0.12.0"
  }
}
```

## 使用 Extension.js 4.1.18 或更早版本的项目

在 4.1.19 之前，`extension/types` 引用了 `chrome`，但不会安装 `@types/chrome`。一个调用了 `chrome.*`、却没有自己那一份类型的项目跑 `tsc` 会失败：

```plaintext
src/background.ts(19,1): error TS2304: Cannot find name 'chrome'.
src/content/scripts.ts(87,30): error TS2503: Cannot find namespace 'chrome'.
```

把 `extension` 升级到 4.1.19 或更高版本。如果你留在更早的版本上，请手动安装这个包：

<CodeGroup>

```bash npm
npm install -D @types/chrome
```

```bash pnpm
pnpm add -D @types/chrome
```

```bash yarn
yarn add -D @types/chrome
```

```bash bun
bun add -d @types/chrome
```

```bash deno
deno add -D npm:@types/chrome
```

</CodeGroup>

在这些版本上，装上 `@types/webextension-polyfill` 之前，`browser` 的类型是 `any`。想为 `browser.*` 提供类型，请把这个包也装上：

<CodeGroup>

```bash npm
npm install -D @types/webextension-polyfill
```

```bash pnpm
pnpm add -D @types/webextension-polyfill
```

```bash yarn
yarn add -D @types/webextension-polyfill
```

```bash bun
bun add -d @types/webextension-polyfill
```

```bash deno
deno add -D npm:@types/webextension-polyfill
```

</CodeGroup>

## 升级后出现类型错误

更早的版本会随 `extension` 一起安装 `@types/chrome`，并用 `webextension-polyfill` 为 `browser` 提供类型。安装了 `@types/chrome` 的项目会保留这些类型。没有 `@types/chrome` 的项目在升级后会改用 `chrome-types`。

改用之后，以前能通过 `tsc` 的代码可能会出现新的类型错误。例如，`tsc` 可能会报告 `chrome.tabs.TabChangeInfo` 这样的名称不存在。

安装 `@types/chrome` 可以保留以前的类型，然后运行一次 `extension dev` 或 `extension build`。`browser.*` 在运行时那一侧的样子，请阅读[跨浏览器兼容性](/zh-Hans/docs/features/cross-browser-compatibility)。

## 让 extension-env.d.ts 留在 include 列表里

只有当 TypeScript 读到它时，这个生成的文件才有用。脚手架生成的 `tsconfig.json` 会点名它：

```json tsconfig.json
{
  "include": ["./", "extension-env.d.ts"],
  "exclude": ["node_modules", "dist"]
}
```

当 Extension.js 为一个还没有 `tsconfig.json` 的项目写下这份文件时，那份文件里不带 `include` 数组。TypeScript 于是会读取项目目录下的每一个文件，所以照样能找到 `extension-env.d.ts`。而一个你自己写的、漏掉了这个文件的 `include` 数组，会让资源导入和 `browser` 全局变量一起失效。

从 4.1.39 之后的版本起，只有当你的 `tsconfig.json` 会在 `package.json` 旁边读到这个文件时，Extension.js 才会创建它。没有 `include` 数组、`include` 覆盖了项目根目录，或者 `include` 或 `files` 点名了这个文件，都属于这种情况。如果 `include` 更窄，例如 `["src"]`，这个文件就不会被创建，所以请把它加进去：

```json tsconfig.json
{
  "include": ["src", "extension-env.d.ts"]
}
```

已经存在的那一份无论如何都会保持最新。重新格式化它，例如换一种引号或去掉分号，不会触发重写。

## 症状与修复

| 症状                                | 原因                                             | 修复                                          |
| ----------------------------------- | ------------------------------------------------ | --------------------------------------------- |
| `Cannot find name 'chrome'`         | Extension.js 4.1.18 或更早，并且没有 `@types/chrome` | 升级到 4.1.19，或安装 `@types/chrome`         |
| `Cannot find namespace 'chrome'`    | 同样的原因，只是出现在类型位置                   | 升级到 4.1.19，或安装 `@types/chrome`         |
| `Cannot find module './styles.css'` | `extension-env.d.ts` 落在 `include` 之外         | 把这个文件加进 `include`                      |
| `Cannot find name 'browser'`        | 项目从来没跑过 `dev` 或 `build`                  | 跑一次任意一条命令来生成类型                  |
| 升级后 `chrome.tabs.TabChangeInfo` 这样的名称不存在 | 项目从 `@types/chrome` 改用了 `chrome-types` | 安装 `@types/chrome`，然后跑一次 `dev` 或 `build` |
| CI 中已提交的 `extension-env.d.ts` 出现类型错误 | `tsc` 在 CLI 重写这个文件之前就运行了 | 在 `tsc` 之前运行 `dev`、`build` 或 `start` |

## 最佳实践

- 把 `extension-env.d.ts` 当作构建产物看待。愿意的话可以提交它，但绝不要编辑它。
- 只有当你需要某个类型包的特定版本，或者想保留 `@types/chrome` 时，才在你自己的 `devDependencies` 里声明它。
- 在持续集成中跑 `tsc --noEmit`。Extension.js 的构建不会因为类型错误而失败。
- 在持续集成中，先跑 `extension build`，再跑 `tsc`。`dev`、`build` 和 `start` 会重新生成 `extension-env.d.ts`，而 `tsc` 不会。
