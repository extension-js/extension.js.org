以每次状态变化一个 JSON 帧的方式跟随一个正在运行的会话。

一个终止信封无法描述一整个会话，因此 `dev`、`start` 和 `preview` 会为每一次生命周期状态变化流式输出一个 schema-1 帧。每个帧本身就是独立成行的一个完整[结果信封](/zh-Hans/docs/contracts/result-envelope)。

## 打开这个流

这个流由 `EXTENSION_OUTPUT` 环境变量控制。把它设为 `json` 或 `ndjson`，帧就会独占 stdout：

```bash
EXTENSION_OUTPUT=ndjson npx extension@latest dev ./my-extension --browser chromium --no-browser
```

流开启期间，原本共用 stdout 的人类可读文案会移到 stderr。错误文案始终留在 stderr，机器模式绝不会隐藏失败。

## 帧的状态

| 状态             | `ok`  | 什么时候到达                                                              |
| ---------------- | ----- | ------------------------------------------------------------------------- |
| `starting`       | true  | 只有一次，会话开始时，即配置加载完成、编译器已创建之后。携带 `requestedPort` 和实际绑定的 `port`。 |
| `compiled`       | true  | 第一次编译成功。携带 `assets` 和 `durationMs`。                           |
| `recompiled`     | true  | 之后每一次编译成功。                                                      |
| `compile-failed` | false | 一次编译带着错误结束，无论是第一次还是之后。                              |
| `ready`          | true  | 本次会话的 `ready.json` 已落盘时。之后的编译清除了 `ready-failed` 或 `load-refused` 时会再次到达。从 4.1.41 之后的版本起，`dev` 重启成功后也会再次到达，并带 `value.restarted: true`。 |
| `browser-exited` | false | 浏览器在会话中途退出，见下文。                                            |
| `restart-failed` | false | 从 4.1.41 之后的版本起。重启无法构建下一个 bundle，所以之前的构建继续提供服务，`value.serving` 为 `true`。`error.code` 是该失败自身的错误码，或者 `E_DEV_SERVER_START`。再次保存改动的文件即可重试。 |
| `load-refused`   | false | 浏览器拒绝了扩展。会话继续运行，并在下一次编译时再次提供扩展。 |
| `ready-failed`   | false | 从 4.1.41 之后的版本起。会话继续运行时 `ready.json` 报告 `error`，例如启动失败。下一次编译会再次尝试。 |
| `warning`        | true  | 从 4.2.0 之后的版本起。会话在两次编译之间警告过的事情，一旦得知就立即写入，比如扩展始终没有确认的重载。`value.code` 和 `value.message` 说明它，`warnings` 中有一条记录。之后的帧不会重复它。 |
| `failed`         | false | 结束本次运行的会话级别失败，例如服务器始终没能绑定，重启时下一个服务器无法启动，或者停止超过了关闭时限。 |
| `usage`          | false | 浏览器启动拒绝了你设置的值时的最后一帧，例如有问题的 `--chromium-binary` 固定路径。 |
| `stopped`        | 视情况 | 最后一帧。会话自行以退出码 `0` 结束时为 `ok: true`。被 `SIGINT` 等信号停止时为 `ok: false`，带 `E_INTERRUPTED` 和 `value.signal`。 |

每个帧的 `value` 都携带会话身份：`command`、`browser`、`distPath`、`pid`、`port`，以及已知时的 `readyPath`、`eventsPath`、`runId`、`instanceId` 和 `toolchainVersion`。

`failed`、`usage` 和 `stopped` 是终止状态。终止帧表示进程正在结束，流在它之后不再写入任何内容，所以读到第一个终止帧就停止。其他每个 `ok: false` 帧都让会话继续运行。当 CLI 知道该错误码的解决办法时，`failed` 或 `usage` 帧会把它放在 `hint` 中。

只有这三种会结束流。读取方忽略它不认识的状态并继续读取，所以之后版本新增的状态不会让它停下。

从 4.2.0 之后的版本起，终端报告的两种重载失败，即扩展始终没有确认的编译和一直没有回来的扩展，也会以带 `W_RELOAD_NOT_APPLIED` 的 `warning` 帧送达。终端文本不带代码。

在会话开始之前就被拒绝的运行只发送一个 `failed` 帧，不会有 `starting` 帧。缺少 manifest、配置文件加载失败，以及远程 URL 没有可用的归档，都以这种方式结束。

## 编译失败

`compile-failed` 帧会把编译器输出放在 `value.output` 里，所以你永远不需要去刮 stdout。这段输出已经去掉 ANSI 控制符，并且上限为 2000 个字符。当上限把它截断时，该帧会设置 `truncated: true`。

一次会话中的第一次失败使用错误码 `E_FIRST_COMPILE`，之后每一次都使用 `E_COMPILE`。

该帧还会携带 `error.details`，每条诊断一个条目，各自带有错误码、文件和位置，错误排在前面，结构见[结果信封](/zh-Hans/docs/contracts/result-envelope)中的"编译诊断"一节。列表上限为 20 条，当输出或列表任一被截断时，都会设置 `truncated: true`。

```jsonl

{"schema":1,"ok":true,"command":"dev","status":"compiled","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4","assets":12,"durationMs":841},"error":null,"warnings":[]}
{"schema":1,"ok":true,"command":"dev","status":"ready","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4"},"error":null,"warnings":[]}
{"schema":1,"ok":false,"command":"dev","status":"compile-failed","value":{"command":"dev","browser":"chromium","distPath":"/home/dev/my-extension/dist/chromium","pid":51234,"port":8080,"runId":"mdyq3k2p-a1b2c3d4","output":"ERROR in ./content/scripts.ts\nModule parse failed: Unexpected token (12:3)","durationMs":204},"error":{"code":"E_COMPILE","message":"A recompilation failed after a change.","details":[{"code":"E_CONTENT_SCRIPT_SYNTAX","message":"Module parse failed: Unexpected token (12:3)","file":"content/scripts.ts","line":12,"column":3,"severity":"error"}]},"warnings":[]}
```

## ready 遵循契约

`ready` 帧在触发之前会读取 `ready.json`。编译可能成功，而浏览器却拒绝了这个扩展，发生这种情况时契约会保持在 `error`。

会话继续运行时，流随后会发出一个 `ready-failed` 帧。浏览器拒绝了扩展时，发出的是 `load-refused`。两者都不会结束会话，之后清除该错误的编译会再次写出 `ready`。只有当进程退出时 `ready.json` 仍报告该错误，契约错误才会变成 `failed` 帧。

`error.code` 是启动器盖上的错误码，否则就是契约状态对应的错误码。例如 `browser_launch_failed` 对应 `E_BROWSER_LAUNCH`，被拒绝的加载对应 `E_EXTENSION_LOAD_REFUSED`。`E_READY_ERROR_STATUS` 只留给没有自身错误码的状态。`value.readyCode` 指出契约自身的错误 id。

浏览器根本没有启动时，会发送这个帧，`value.readyCode` 为 `browser_launch_failed`。Firefox 的调试器始终没有应答时，按启动失败处理。浏览器退出时发送的则是 `browser-exited` 帧，见下文。

`--chromium-binary` 或 `--gecko-binary` 固定的二进制有问题时，`readyCode` 同样是 `browser_launch_failed`，但其帧带 `status: "usage"` 与 `error.code: "E_BROWSER_BINARY_INVALID"`，这也是每个命令对这种固定路径给出的代码。

Chromium 的 `dev` 会话在浏览器起来之后 CDP 连线失败时，仍然会发送 `ready`，因为浏览器在运行。该帧会把故障放在 `warnings` 里，形式为 `W_CDP_...: message`，与契约盖上的 `cdpFaultCode` 和 `cdpFaultMessage` 是同一对值，见 [ready.json](/zh-Hans/docs/contracts/ready-json)。在故障修复前，reload 和 HMR 无法接上。

## 浏览器退出

一个后台监视器每秒轮询一次 `ready.json`，查找启动器写下的退出戳记。当 `browserExitedAt` 出现时，流会发出一个 `browser-exited` 帧。

这个帧的错误码取决于契约里的证据：

- `E_PROFILE_LOCKED`：契约显示配置文件被锁定。浏览器根本没有启动，另一个会话正占用该配置文件。
- `E_BROWSER_LAUNCH`：其余所有意外退出。

当契约中有这些字段时，帧的 `value` 会携带 `exitCode`、`exitSignal` 和 `browserExitedAt`。崩溃没有退出码，只有 `SIGTRAP` 这样的信号。

从 4.1.41 之后的版本起，`browser-exited` 或 `ready-failed` 帧的 `hint` 以 CLI 对该错误码已知的解决办法开头，然后说明会话继续运行。对于 `E_PROFILE_LOCKED`，解决办法是关闭打开了该配置文件的浏览器，或者传入 `--profile <path>`。

## 重启与关闭

从 4.1.41 之后的版本起，下一个 bundle 无法构建的重启会发送一个 `restart-failed` 帧，旧服务器继续提供服务。如果旧服务器停止后下一个服务器无法启动，流会发送 `failed`，进程以 `1` 退出。

从 4.1.41 之后的版本起，`dev` 重启成功后，新服务器的第一次编译通过时会再次写出 `ready`。该帧的 `value` 携带 `restarted: true`。在那之前，流照常写出编译帧。

关闭有 10 秒时间完成，之后进程以 `1` 退出。在第一次 `Ctrl+C` 一秒多之后再按一次，也会立即强制以 `1` 退出。被强制的关闭永远不会报告成功。

从 4.1.41 之后的版本起，如果之前没有写出终止帧，超过这个时限的停止会以带 `E_SHUTDOWN_TIMEOUT` 的 `failed` 结束流。自动退出期限触发的停止就是一个例子。该帧的 `value` 携带 `exitCode` 和 `shutdownTimeoutMs`。由信号触发的停止保留它的 `stopped` 帧。

从 4.2.0 之后的版本起，`preview` 和 `start` 也以同样的方式结束流。收到 `SIGINT` 或 `SIGTERM` 时，最后一帧是带 `E_INTERRUPTED`、`value.signal` 和 `value.browsers`（本次运行面向的浏览器）的 `stopped`，随后运行以 `0` 退出。

从 4.2.0 之后的版本起，在命令写出任何帧之前到达的信号，仍会以一个带 `E_INTERRUPTED` 和 `value.signal` 的 `stopped` 帧结束流。`SIGINT` 时运行以 `130` 退出，`SIGTERM` 时以 `143` 退出。

以 `0` 以外的退出码结束的会话同样以终止帧结束。`ready.json` 中有错误时，该帧携带那个错误的错误码。否则就是带 `E_INTERNAL` 和 `value.exitCode` 的 `failed`。
