只要轮询一个 JSON 文件，就能知道一个会话是就绪、出错，还是已经没了。

每一次 `dev`、`start`、`preview` 和 `build` 运行，都会在每次编译时原子地写入 `dist/extension-js/<browser>/ready.json`。当前契约是 `schemaVersion: 2`。

没有构建产物的 `preview` 会加载源码目录，但仍然把契约写到项目的 `dist/extension-js/<browser>/ready.json`，并带有已构建的 preview 所带的全部浏览器字段。

## 状态

| 状态       | 含义                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| `starting` | 这次运行开始了。文件被重置，`events.ndjson` 也为本次运行清空。                          |
| `ready`    | 最近一次编译成功，输出已经在磁盘上。从 4.1.41 之后的版本开始，在需要启动浏览器的 `dev` 下，启动器也已经盖上了它的字段。见[两阶段就绪](#两阶段就绪)。 |
| `error`    | 编译失败，浏览器根本没有启动或在扩展加载之前就退出了，或者浏览器拒绝了、丢掉了这个扩展。 |
| `stopped`  | 监听已关闭。会盖上 `code: "shutdown"`，这样一个已经死掉的会话永远不会宣称自己 `ready`。 |

## 两阶段就绪

`status: "ready"` 只意味着编译完成。浏览器可能还在启动（下面说明的 `dev` 情形除外），service worker 也可能还没有连上。

从 4.1.41 之后的版本开始，在需要启动浏览器的 `dev` 下，编译之后 `status` 仍保持 `starting`，等启动器盖上 `browserPid`、`binary`、`profilePath` 和调试器端口（Chromium 上是 `cdpPort`，Firefox 上是 `rdpPort`）之后才变为 `ready`。`executorAttachedAt` 可以出现在 `ready` 之后，除非会话是带 `--allow-control` 或 `--allow-eval` 启动的，这时 `ready` 会等它，最多 10 秒。

在 Chromium 的 `dev` 会话里，stdout 上的 `ready` 行是更严格的声明：只有扩展内部的运行时连上之后（`executorAttachedAt`），启动器才会打印它。如果浏览器已经启动，而 15 秒内没有任何东西连上，启动器会改为打印它在等什么，盖上 `browserUpNotAttachedAt` 和一条提示，并在 attach 到达的那一刻打印 `ready`。

act 类工具（`eval`、`storage`、`reload`、`open`、`inspect`）需要第二个阶段。要等到契约里带上 `runtime: "attached"` 和一个 `executorAttachedAt` 时间戳之后，再去驱动扩展。

attach 这个戳是幂等的，并且能挺过重新编译。一次 attach 也会清除之前的 `extension_load_refused` 状态，因为执行器就跑在被托管的浏览器里面。

### 接受 act 命令的会话会按住 ready

从 4.1.39 之后的版本起，接受 act 命令的会话会保持 `status: "starting"`，直到扩展的 background 连上，或者过去 10 秒。适用的情形是：

- 带 `--allow-control` 或 `--allow-eval` 的 `preview` 与 `start`。没有 background 的构建不会等待，因为它没有任何东西会来连接。
- 带 `--allow-control` 或 `--allow-eval`，并且由会话启动浏览器的 `dev`。

`dev` 等待期间，契约里带有 `awaitingExecutorSince`。background 连上或者等待结束之后，这个字段就会消失。

等待有上限，所以从不连接的扩展仍然会得到 `ready`，只是旁边没有 `executorAttachedAt`。说明 act 命令可以运行的字段仍然是 `executorAttachedAt`。

在 Firefox 上，处于等待中的 `dev` 会话要同时有 RDP 端口和 background，才会报告 `ready`。

## 字段参考（schema v2）

始终存在的字段：

| 字段               | 类型           | 含义                                                                         |
| ------------------ | -------------- | ---------------------------------------------------------------------------- |
| `schemaVersion`    | `2`            | 就绪契约自身的版本。                                                         |
| `schema`           | `1`            | 表明这个引擎讲的是 schema-1 的[结果信封](/zh-Hans/docs/contracts/result-envelope)。  |
| `status`           | string         | `starting`、`ready`、`error` 或 `stopped`。                                  |
| `command`          | string         | `dev`、`start`、`preview` 或 `build`。                                       |
| `browser`          | string         | 这个会话服务的浏览器目标。                                                   |
| `runId`            | string         | 会话身份。在 `ready.json`、`events.ndjson` 和 `logs.ndjson` 之间做连接的键。 |
| `startedAt`        | ISO string     | 这次运行开始的时间。                                                         |
| `distPath`         | string         | 编译后扩展的绝对路径。                                                       |
| `manifestPath`     | string         | 源 manifest 的绝对路径。                                                     |
| `port`             | number 或 null | dev 服务器实际绑定的端口。                                                   |
| `pid`              | number         | dev 服务器进程 id。在信任这份契约之前，先确认它还活着。                      |
| `pidStartedAt`     | ISO string     | 从 4.1.40 起，`pid` 背后的进程启动的时间。被复用的 pid 有另一个启动时间，所以两者都要比对。 |
| `pidStartId`       | string         | 从 4.2.0 之后的版本起，仅限 Linux：`pid` 的 boot id 与内核启动 tick，用冒号连接。时钟跳变（比如恢复的虚拟机或 WSL2）会改变 `pidStartedAt`，但永远不会改变这个值。当你能为存活的 pid 读到它时，用相等比较它，而不是比较日期。 |
| `ts`               | ISO string     | 这份文档最后一次被写入的时间。从 4.2.0 之后的版本起，是 `status` 最后一次被写入的时间：写在状态旁边的事实不会改变它。                                               |
| `compiledAt`       | string 或 null | 最近一次成功编译完成的时间。                                                 |
| `errors`           | string[]       | 去掉 ANSI 转义的编译错误，最多 10 条。                                       |
| `toolchainVersion` | string         | 产出这棵目录树的 Extension.js 版本。                                         |

| `instanceExplicit`   | boolean        | 实例 id 是否由用户指定。                                                                                                                                           |

| `controlPortUnavailableReason` | string | 会话请求了控制通道而 `controlPort` 为 null 时的原因。 |

| `cdpPort`            | number         | Chromium 启动时：CDP 端口，在启动之后盖章。从 4.1.41 之后的版本开始，同时启动的会话各自拿到自己的调试端口，所以请读取这个字段，不要假定是 9222。在 `preview` 和 `start` 上，卡片打印时它已经在记录里。 |
| `rdpPort`            | number         | Gecko 启动时：RDP debugger-server 端口，在启动之后盖章。从 4.1.41 之后的版本开始，同时启动的会话各自拿到自己的端口，所以请读取这个字段。 |
| `rdpPortError`       | string         | Gecko 启动时，从 4.1.39 起：Firefox 为何没有打开远程调试端口。此时没有 `rdpPort`。 |
| `webdriverPort`    | number   | Safari 的 `dev` 会话：启动器在应用旁持有的 safaridriver 会话端口。Safari 一次只允许一个自动化会话，请接到这个会话而不是自己再开一个。 |
| `webdriverSessionId` | string | 与 `webdriverPort` 并列的会话 id。 |
| `webdriverUnavailableReason` | string | 启动器为何没有持有 WebDriver 会话，例如 Safari 的"允许远程自动化"是关闭的，或者请求会话时另一个 Safari 正开着。 |
| `webdriverRequestPath` | string | Safari 的 `dev` 会话：客户端 touch 这个文件即可请求启动器开一个新的 WebDriver 会话。 |
| `safari`           | object   | Safari 的 `dev` 会话：启用步骤走到了哪一步、为何停下，不必再解析会话日志。`bundleId`、`extensionId` 和 `team` 说明 Safari 登记的 appex，`switchId` 是 Safari 设置里的那一行，`enableAttempted` 表示是否运行了 `--enable-extension`，`step` 是到达的最后一步（`not-asked`、`accessibility`、`safari`、`unsigned`、`pluginkit`、`enabled`、`websites`、`done`），`enabled`、`listed` 和 `otherWebsites` 是开关的读数，`reason` 是停下时的那句话，`earlierExtensionIds` 是 macOS 仍列出的本项目早先构建的 id，它们的开关不会带到新 id 上。 |
| `cdpFaultCode`       | string         | Chromium 的 `dev` 会话：浏览器起来之后 CDP 连线失败时盖上，值是调试协议警告码之一，例如 `W_CDP_TIMEOUT` 或 `W_CDP_NOT_CONNECTED`。4.1.41 及更早的版本盖上的是 `E_*` 名称。因为浏览器在运行，会话保持 `ready`，但在故障修复前 reload 和 HMR 无法接上。同一次运行跨重新编译保留。 |
| `cdpFaultMessage`    | string         | 与 `cdpFaultCode` 并列的一行纯文本。`--output json` 下的 `ready` 帧会把同一故障放在 `warnings` 里，形式为 `W_CDP_...: message`。 |
| `browserUpNotAttachedAt` | ISO 字符串 | Chromium `dev` 会话：浏览器进程已启动且扩展已编译，但扩展内部的运行时在启动器的宽限期（15 秒）内没有连接到控制桥时写入。状态保持 `ready`，stdout 上的 `ready` 行会推迟到连接建立后再打印。首次连接后清除。 |
| `browserUpNotAttachedWaitMs` | number | 启动器在写入 `browserUpNotAttachedAt` 之前等待的毫秒数。 |
| `browserUpNotAttachedHint` | string | 并列的纯文本说明：浏览器及其 pid、配置目录路径、该目录此前是否被运行过，以及改用全新配置目录的做法。 |
| `profileReused` | boolean | Chromium 启动：此次启动之前是否已有浏览器用过该配置目录。被复用的配置目录是浏览器启动后却没有任何连接的常见原因。 |
| `profilePath`        | string         | 解析出来的配置文件目录。临时配置文件的名字是生成的，所以要从这里读。                                                                                               |
| `binary`             | string         | 这个会话实际启动的浏览器二进制文件的绝对路径。每次运行都会盖章，包括那些没有指定二进制文件的运行：恰恰是在那些运行里，解析器替你做了选择，而这个路径在别处看不到。 |
| `binaryProvenance`   | string         | 这个二进制是怎么选出来的：`managed`（Extension.js 的缓存）、`pinned`（二进制 flag 或二进制变量）、`system`（已安装的浏览器）或 `snapshot`（缓存的 dev 频道构建）。 |
| `binaryPinnedBy`     | string         | 从 4.1.39 之后的版本起：指明 `pinned` 二进制的那个 flag 或变量，例如 `--chromium-binary` 或 `FIREFOX_BINARY`。其他来源下不出现。 |
| `browserPid`         | number         | 浏览器进程 id。这是拆掉浏览器时受支持的句柄。                                                                                                                      |
| `browserStartedAt`   | ISO string     | 从 4.1.40 起，`browserPid` 背后的进程启动的时间，用来识别被复用的 pid。进程表无法给出时间时没有这个字段。 |
| `launcherPid`        | number         | 从 4.1.22 起，启动器所派生的进程。浏览器把会话交给另一个进程时它仍会保留。`browserPid` 指向存活的那个。 |
| `launcherStartedAt`  | ISO string     | 从 4.1.40 起，`launcherPid` 背后的进程启动的时间。 |
| `extensionId`        | string         | 浏览器用来提供这份 dist 的 id。能拿到时由浏览器确认，否则是推导出来的。从 4.1.41 之后的版本开始，契约记录着加载被拒时没有这个字段，除非浏览器自己确认了这个 id。 |
| `extensionIdSource`  | string         | 从 4.1.35 起，`extensionId` 的来源：`browser`、`derived` 或 `packager`。 |
| `extensionBaseUrl`   | string         | Firefox 启动，从 4.1.39 之后的版本起：浏览器提供这个扩展所用的 `moz-extension://<uuid>/` 地址。Firefox 按配置文件选定这个 UUID，所以从附加组件 id 看不出它。 |
| `devAdditions`       | array          | `dev` 会话，从 4.1.39 之后的版本起：会话有而生产构建没有的东西。见[开发附加项](#开发附加项)。 |
| `extensionName`      | string         | 扩展的名字，作为构建溯源信息。                                                                                                                                     |
| `extensionVersion`   | string         | 扩展的版本，作为构建溯源信息。                                                                                                                                     |
| `browserExitedAt`    | ISO string     | 浏览器在会话中途、没被要求就退出时盖上。跨重新编译保留。                                                                                                           |
| `browserExitCode`    | number 或 null | 与 `browserExitedAt` 并列的退出码。                                                                                                                                |
| `browserExitSignal`  | string 或 null | 浏览器死于某个信号时，与 `browserExitedAt` 并列的信号，比如崩溃时的 `SIGTRAP`。崩溃不带退出码，所以这是说明它为什么退出的唯一线索。 |
| `browserLaunchFailedAt` | ISO string | 根本没有任何浏览器进程起来时盖上。跨重新编译保留。 |
| `browserLaunchFailedReason` | string | 与 `browserLaunchFailedAt` 并列的原因，写成一行纯文本，比如带着二进制路径的 spawn 错误。 |
| `extensionLoadRefusedAt` | ISO string | 浏览器拒绝加载扩展时打上的时间戳。从 4.1.41 之后的版本开始，已停止的契约会保留它。 |
| `extensionLoadRefusedReason` | string | 与 `extensionLoadRefusedAt` 并列的浏览器原因。从 4.1.41 之后的版本开始，已停止的契约会保留它。 |
| `extensionLoadRefusedCause` | string | 从 4.1.41 之后的版本开始。当启动器从 manifest 得知浏览器为什么拒绝、而浏览器的原话没有说明时出现。已停止的契约会保留它，它会随拒绝一起被清除。 |
| `runtime`            | `"attached"` 或 `"detached"` | service worker 连上并且可以被驱动后为 `attached`。从 4.1.20 起，最后一个已连接的扩展上下文断开后为 `detached`，重新连接后又回到 `attached`。 |
| `executorAttachedAt` | ISO string     | service worker 第一次连上的时间。断开后会作为来源记录保留。 |
| `executorDetachedAt` | ISO string     | 从 4.1.20 起，最后一个已连接的扩展上下文断开的时间。 |
| `awaitingExecutorSince` | ISO string | `dev` 会话，从 4.1.39 之后的版本起：会话开始为 background 按住 `ready` 的时间。background 连上或过去 10 秒之后移除。 |
| `managedExtensions`  | array          | 除了你的扩展之外、引擎还加载的每一个扩展，形式是 `{path, id?}` 记录。做统计时按 id 把它们减掉。                                                                    |
| `reloadedAt`         | ISO string     | `dev` 会话，从 4.1.34 起：编译之后最近一次重新加载生效的时间。`reloadedAt` 晚于某次编译的 `compiledAt` 时，那次编译的重新加载就已生效。不触发重新加载的编译不会改动这个戳。 |
| `reloadKind`         | string         | 那次重新加载的类型：`full`、`background`、`content`、`page` 或 `safari-resync`。 |
| `reloadLabel`        | string         | 那次重新加载的简短标签，有的话才会出现。 |
| `endedAsFailedAt`    | ISO string     | 从 4.2.0 起，会话以失败结束时盖上。从那以后状态读作 `error`。 |
| `endedAsFailedCode`  | string         | 从 4.2.0 起，结束会话的 `E_*` 代码，比如 `E_CONFIG_LOAD`。`--wait` 会先用这个代码作答，再看 `code` 所对应的代码。 |

## 开发附加项

从 4.1.39 之后的版本起，`dev` 契约会列出会话有、而同一份源码的生产构建没有的东西。每个 `devAdditions` 条目都带有 `kind`、`value` 和 `reason`：

| `kind`                    | `value`                                        | 额外字段                                                  |
| ------------------------- | ---------------------------------------------- | --------------------------------------------------------- |
| `permission`              | dev manifest 添加的权限，例如 `scripting`。    | 无                                                        |
| `host_permission`         | dev manifest 添加的主机匹配模式。              | 无                                                        |
| `web_accessible_resource` | dev manifest 暴露的资源，例如 `hot/*`。        | `matches`，可以读取它的来源。Manifest V2 下不出现。       |
| `manifest_change`         | 其他仅限 dev 的 manifest 改动，例如 `background.persistent true` 或 `externally_connectable.ids *`。 | 无 |
| `browser_flag`            | 一个会改变你在浏览器里所见内容的启动 flag。    | `applied`、`cause` 和 `change`。                          |
| `browser_preference`      | 会话写进被保留的 profile 的浏览器偏好，形式为 `name=value`。 | `applied`、`cause` 和 `change`。 |

前四种是你的 manifest 与 dev manifest 之间的差异。从 4.1.41 之后的版本起，`manifest_change` 会报告其他仅限 dev 的改动：更宽松的页面策略、重新开放的 `externally_connectable` 列表、新增的 background，以及保持常驻的 background。每次重新编译都会替换它们。`browser_flag` 与 `browser_preference` 条目由启动器写入，重新编译会保留它们。

`browser_flag` 条目说明这次启动是否传入了该 flag（`applied`），以及是什么决定了这一点（`cause`）。`cause` 的取值是 `default`、`browser-flags`、`debugger-permission` 或 `exclude-browser-flags`。`change` 写明能把结论反过来的那一处修改。

当 profile 比会话活得更久时（例如 `--profile <path>`），Chromium 上会出现一个 `browser_preference` 条目。会话把 `session.restore_on_startup` 设为 `5`，这样 Chrome 会打开新标签页，而不是恢复上一次运行的页面。会话结束后，这个值仍然留在那个 profile 里。它的 `cause` 是 `default`；你的配置设置了这个偏好时是 `preferences`；浏览器拒绝写入时是 `unavailable`。见[浏览器偏好设置](/zh-Hans/docs/browsers/browser-preferences#保留的-profile-上的启动偏好)。

```json
{
  "devAdditions": [
    {
      "kind": "permission",
      "value": "scripting",
      "reason": "the dev reload registers content scripts and injects the rebuilt files into open tabs"
    },
    {
      "kind": "web_accessible_resource",
      "value": "hot/*",
      "matches": ["https://example.com/*"],
      "reason": "a content script fetches its hot update chunks from the page"
    },
    {
      "kind": "browser_flag",
      "value": "--silent-debugger-extension-api",
      "applied": false,
      "cause": "debugger-permission",
      "reason": "the manifest declares \"debugger\", so the debugging bar and its Cancel button show as they do for a user",
      "change": "list the flag under browserFlags in extension.config.js to hide the bar"
    }
  ]
}
```

身份卡会把同样的条目打印成 `Dev only` 与 `Dev flag` 行。见[读懂 CLI 输出](/zh-Hans/docs/concepts/reading-cli-output#卡片下方的行)。有两个 flag 跟随 `debugger` 权限。见[浏览器 flag](/zh-Hans/docs/browsers/browser-flags#debugger-权限会改动两个-flag)。

## 错误状态

`code` 字段给失败类别命名。对自动化来说有四个代码要紧：

| `code`                   | 发生了什么                                                                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `extension_load_refused` | 会话在跑，但浏览器把扩展扔了出去。其他每一个界面看起来都正常，只有契约会告诉你。从 4.1.41 之后的版本开始，act 命令（`eval`、`storage`、`reload`、`inspect`、`navigate`）会回答 `E_EXTENSION_LOAD_REFUSED` 并附上浏览器给出的原因，`doctor` 会在 `ready-contract` 一行指出它。带 `extensionLoadRefusedAt` 与 `extensionLoadRefusedReason`。从 4.1.41 之后的版本开始，启动器知道原因时还会带 `extensionLoadRefusedCause`。 |
| `profile_locked`         | 另一个活着的会话占着这个配置文件，所以浏览器根本没有启动。带 `profileLockedAt` 和一个含 `host` 与 `pid` 的 `profileLockOwner`。               |
| `browser_exited`         | 浏览器进程死了。`start` 和 `preview` 会翻成 `error`。`dev` 只有在浏览器先于扩展加载就退出时才翻成 `error`。过了那个点，`dev` 保持它的编译状态，只盖上 `browserExitedAt`。Firefox 在调试器应答之前就退出时，大约一秒内落到这里。 |
| `browser_launch_failed`  | 没有任何浏览器进程起来：二进制不存在、无法执行，或者固定的路径不对。Firefox 在运行但调试器始终没有应答时也落到这里，Extension.js 会结束那个进程。`dev`、`start` 和 `preview` 都会翻成 `error`。带 `browserLaunchFailedAt` 与 `browserLaunchFailedReason`。因固定的 `--chromium-binary` 或 `--gecko-binary` 有问题而被拒绝的启动还会带 `browserLaunchFailedCode: "E_BROWSER_BINARY_INVALID"`。Gecko 浏览器在系统 profile 模式下被拒绝的启动会带 `browserLaunchFailedCode: "E_FLAG_NOT_SUPPORTED_HERE"`。 |

从 4.2.0 起，在编译之前就被拒绝的 `build`（比如因为不合法的 [`perfBudgets`](/zh-Hans/docs/workflows/performance-playbook) 值）会把已有的 `ready.json` 标记为 `status: "error"` 与 `code: "build_failed"`。拒绝本身的代码写在 `endedAsFailedCode`。从未构建过的项目不会得到这个文件，存活中的 `dev` 会话的文件也不会被改动。
一次加载被拒会活过下一次成功编译。只有一次新的运行（`starting`）或者一次真正的执行器 attach 才能把它清掉。从 4.1.41 之后的版本开始，已停止的契约会保留 `extensionLoadRefusedAt`、`extensionLoadRefusedReason` 和原因。

浏览器在扩展加载之前就退出的 `dev` 会话，会跨重新编译一直停在 `error`，因为重新编译不会把浏览器带回来。启动失败同样会活过重新编译，直到真的有一个浏览器启动，或者开始一次新的运行。

从 4.2.0 之后的版本起，启动器写入的每个字段都会在同一次运行的重新编译之间保留。浏览器判定（`browser_exited`、`browser_launch_failed`、`profile_locked` 或 `extension_load_refused`）在一次成功的编译之后仍保留 `status: "error"`、它的 `code` 和 `message`。只有 `compile_error` 与 `compile_failed` 会在下一次成功编译时清除。

## 用 --wait 等待

`extension dev --wait` 和 `extension start --wait` 每 250 毫秒轮询一次契约，并在它报告 `ready` 时退出。配合 `--output json` 可以拿到机器可读的结果。

等待循环拒绝相信过期文件。每次读取都会跑三项检查：

1. `command` 字段必须与正在等待的命令一致。
2. `pid` 必须还活着。对 `dev` 来说，生产者已死就一定意味着文件过期，所以轮询会继续。
3. 对 `start` 来说，只有当契约足够新鲜时，才接受一个已死的 pid。新鲜的意思是 `ts`、`compiledAt` 或 `startedAt` 在最近 60 秒之内。

超时会以 `E_READY_TIMEOUT` 退出。处于 `error` 状态的契约会带着它的 message 让等待失败，结果里的 `error.code` 由契约自身的代码解析而来：

| 契约的 `code`             | `--wait` 的错误码          |
| ------------------------- | -------------------------- |
| `compile_error`           | `E_COMPILE`                |
| `compile_failed`          | `E_COMPILE_FATAL`          |
| `build_failed`            | `E_COMPILE`                |
| `dev_server_start_failed` | `E_DEV_SERVER_START`       |
| `browser_launch_failed`   | `E_BROWSER_LAUNCH`         |
| `browser_exited`          | `E_BROWSER_EXITED`         |
| `profile_locked`          | `E_PROFILE_LOCKED`         |
| `extension_load_refused`  | `E_EXTENSION_LOAD_REFUSED` |
| 不在这张表里的代码        | `E_READY_ERROR_STATUS`     |

从 4.2.0 起，带 `endedAsFailedCode` 的契约会先以该代码让等待失败。
带 `browserLaunchFailedCode: "E_BROWSER_BINARY_INVALID"` 或 `"E_FLAG_NOT_SUPPORTED_HERE"` 的 `browser_launch_failed` 契约会让等待以该代码和 `status: "usage"` 失败，而不是 `E_BROWSER_LAUNCH`。

从 4.1.41 之后的版本开始，对因拒绝而结束的运行使用 `--wait`，会立刻回答 `E_EXTENSION_LOAD_REFUSED`，不会等到 `E_READY_TIMEOUT`，除非 manifest 在拒绝之后发生了变化。

## 把会话文件连起来

同一个目录里还放着 `events.ndjson`（编译时间线）和 `logs.ndjson`（扩展的控制台输出）。这两个文件里的每一行都带着来自 `ready.json` 的 `runId`。

`events.ndjson` 在每次运行开始时被清空，所以它永远只描述当前这次运行。事件类型有 `compile_start`、`compile_success`、`compile_error`、`browser_exited`、`browser_launch_failed` 和 `shutdown`。从 4.2.0 之后的版本起，`restart_failed` 行记录一次无法完成的 `dev` 重启，比如配置或入口变更之后，下一个编译器或服务器失败了。它带有错误 `code`、`reason` 和 `serving`：重启之前的构建仍在为会话服务并会在下一次变更时重试时为 `true`，没有服务器留下、会话结束时为 `false`。`browser_exited` 这一行对应启动器盖下的退出戳，带 `exitCode`、`exitSignal` 和 `browserExitedAt`，所以时间线会说明浏览器是什么时候、怎么走的。在它之后，每个 act verb 都会回答 `E_CONTROL_UNAVAILABLE`，并指出这次退出和需要的重启，因为在新的 `dev` 会话重新启动浏览器之前，不会有 service worker 重新连上。`browser_launch_failed` 这一行对应启动失败的戳，带 `browserLaunchFailedAt` 和 `reason`。
