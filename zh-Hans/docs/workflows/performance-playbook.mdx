扩展中的性能回归往往来自很短的一类源头。最常见的是 service worker 冷启动(初始启动延迟)、过重的 content-script 注入、过大的 UI bundle，以及含大量媒体的 web-accessible resources。

下面的检查清单把每种类型映射到具体的修复方法。

## 性能优化能力

| 区域            | 帮你优化什么                                                     |
| --------------- | ---------------------------------------------------------------- |
| content scripts | 注入成本、DOM 工作时机、以及重新挂载的开销                       |
| service worker  | 启动路径、事件处理成本、以及冷启动行为                           |
| UI 界面         | 初始渲染体积与可选功能的加载                                     |
| 资产            | bundle 大小、图标/媒体体积、以及 web-accessible resources 的占用 |
| 运维            | 持续集成 (CI) 检查与运行时回归追踪                               |

## 快速优化过程

1. 在一个目标浏览器上测量首次运行的行为。
2. 削减 content scripts 与后台处理器中的同步启动工作。
3. 把可选 UI 功能延后到初始渲染之后再加载。
4. 复核构建产物的体积并冒烟测试关键流程。

## Content scripts

- 让入口文件保持小巧，把非关键工作延后。
- 避免在 `document_start` 进行重的同步 DOM 扫描。
- 对 observer 和事件监听器划定作用域；在重新挂载/卸载时清理。
- 把可复用逻辑拆到共享模块，但避免脆弱的动态 import 模式。

## 后台/service worker

- 启动时尽量少做事；在事件到达时再懒初始化。
- 在安全的情况下缓存稳定的计算状态。
- 避免在事件处理器中执行长时间的同步任务。
- 在活跃开发期间关注 service worker 依赖的频繁变化。

## UI 界面(popup / options / 新标签页 / sidebar)

- 让初始渲染路径保持轻量。
- 按需加载较大的可选 UI 功能。
- 在本地调试会话中按需使用框架的 dev tools。
- 让样式模块化，避免巨大的全局 CSS。

## 资产与资源

- 按目标用途优化图标/图片大小。
- 把 web-accessible resources (WAR) 的暴露范围限制到必需的资产。
- 让 public 资产保持有意而为；移除过期文件。
- 定期检查生成的 `dist/<browser>` 产物体积。

## 精简发布的内容

`dist/<browser>` 里的每一个字节，都是每位用户在安装时和每次更新时要下载的字节，而 content script 的资产会随它一起进入每个匹配的页面。下面说明 `extension build` 已经排除了什么、剩余的体积来自哪里，以及到哪里读取这个数字。

**构建排除了什么。** 产物从 `manifest.json` 出发并沿着引用走。它会发布 manifest 指名的条目(background、content script、页面、图标、locale)、这些条目导入的模块和资产，以及 `public/` 下的全部内容。`src/` 里没有任何东西引用的文件不会被输出。一个笔记文件、一个未使用的模块、一个 fixture 文件夹，或者图标旁边的一张多余图片，永远不会进入 `dist/`。你不需要为它们准备忽略列表。

**`public/` 与导入的资产。** 这两条路径的行为不同，而这个差异正是多余字节的常见来源：

- `public/` 会原样复制到产物根目录，连同文件夹结构，并且不做任何检查。那里的过期文件也会被发布。请把这个文件夹当作你决定要发布的文件清单，并修剪它。
- 从 JavaScript 导入的资产会落在 `assets/<name>.<hash>.<ext>`，只发布一次，而且只在导入存在时才发布。
- 从 HTML 页面引用的资产会写两份：一份在 `assets/<relative path>` 下，一份在它的源路径上，这样脚本代码里的引用仍然可用。一个既被 HTML 页面引用又被 JavaScript 导入的文件会发布三份。请从 JavaScript 导入共享图片，或者把它移到 `public/` 并按根路径引用，这样它只会写一份。

**`web_accessible_resources` 的范围。** 在 Manifest V3 上，构建会在你所有 content script 的 `matches` 并集之下，把两类文件加入 `web_accessible_resources`：content script 通过 `import()` 加载的每个 chunk，以及 `assets/` 下每个非脚本文件，无论是哪个页面或脚本把它放在那里的。从 `public/` 复制的文件不会被加入。由此有两个结论。让 `matches` 保持在功能允许的最窄范围。把只给页面用的图片放在 `assets/` 之外(从 `public/` 按根路径引用它们)，这样 content script 的 `matches` 就不会暴露它们。参见[让网页能读取扩展文件](/zh-Hans/docs/implementation-guide/web-accessible-resources)。

**读取体积。** `extension build` 会打印产物的树形结构及每个文件的大小，并以总计收尾：

```plaintext
⏵⏵⏵ Extension built for production in dist/chromium (171.6 KB).
```

带上 `--zip` 时，第二行会给出压缩包的名字和压缩后的大小。压缩包只包含 `dist/<browser>` 的内容，别无其他，位于 `dist/<name>-<version>-<browser>.zip`，其中 name 是 manifest 的 `name` 转为小写并去掉标点：

```plaintext
⏵⏵⏵ Packaged dist/trimdemo-1.0.0-chromium.zip (142.9 KB).
```

在脚本里，`extension build --output json` 会返回 `total_bytes`、`largest_asset_bytes` 以及 `zip_artifacts` 中每一项的大小，同样的摘要还会写到 `dist/extension-js/<browser>/build-summary.json`。在 CI 里跨提交比较 `total_bytes`，就能在商店审核发现之前抓住体积回归。参见 [`build`](/zh-Hans/docs/commands/build)。

## 性能预算

当某个 bundle 超出其分类的体积预算时，生产构建(`build`) 会输出**警告**。预算在生产模式下默认启用，默认情况下超出预算只会警告。

| 分类                                                     | 默认预算 | 原因                                             |
| -------------------------------------------------------- | -------- | ------------------------------------------------ |
| Content scripts                                          | 512 KiB  | 每次匹配页面导航都会注入。                       |
| Service worker                                           | 512 KiB  | 每个事件都可能冷唤醒；过大的 bundle 会拖慢启动。 |
| Pages / UI (popup、options、sidebar、devtools、新标签页) | 1 MiB    | 按需打开。                                       |
| 共享 chunk                                               | 512 KiB  | 每个导入它的页面都会加载。                       |
| Public(从 `public/` 复制的代码文件)                      | 1 MiB    | 按原样发布，所以要在源文件上修。                 |
| Runtime(输出根目录的代码文件，以及 content script 或 service worker 会访问到的 `.wasm` 文件) | 1 MiB | wasm 核心的同级辅助文件，例如 `ffmpeg-core.js`，以及每次导航或冷启动都会获取的 wasm 二进制文件。 |
| WebAssembly(只有页面和 worker 会访问到的 `.wasm` 文件) | 32 MiB | onnxruntime 或 ffmpeg 这样的运行时是一个无法拆分的文件，只在对应功能运行时才获取。 |

在 [`extension.config.js`](/zh-Hans/docs/features/extension-configuration) 中通过 `perfBudgets` 覆盖任一分类(值以字节计)：

```js
export default {
  perfBudgets: {
    "content-script": 768 * 1024,
    "service-worker": 512 * 1024,
    page: 2 * 1024 * 1024,
    shared: 512 * 1024,
    public: 2 * 1024 * 1024,
    runtime: 8 * 1024 * 1024,
    wasm: 16 * 1024 * 1024,
    ignore: ["assets/ort-wasm-simd-threaded.asyncify.wasm", "assets/models/**"],
  },
};
```

要在超出预算时让构建失败，请在 `perfBudgets` 中设置 `onExceed: 'error'`。需要 4.1.41 之后的版本。此时超出预算是错误码为 `E_PERF_BUDGET` 的错误，构建以 `1` 退出。没有该设置，或设置 `onExceed: 'warn'` 时，超出预算会以 `W_PERF_BUDGET` 警告。`onExceed` 的其他任何值都会以 `E_CONFIG_LOAD` 停止构建。

`ignore` 让单个资源不受任何预算约束。按警告打印的方式列出输出路径，即相对于构建目录的路径。在模式中，`*` 匹配单个目录内的内容，`**` 可以跨目录。

预算按从弱到强的顺序分层：顶层，然后是 `browser.<vendor>`，然后是 `commands.build`。从 4.1.41 之后的版本起，只设置一个分类的层会保留其他层设置的分类。较强层中的 `ignore` 列表会替换较弱层的列表。

### 警告列出的内容

警告会列出每个超出预算的文件，最大的排在最前，并给出它的体积、适用的预算和它的角色：

```plaintext
  sidebar/chunk-0.js
    size:   2.00 MiB
    budget: 1.00 MiB  (over by 100%)
    role:   UI page, opened on demand
```

从 4.1.41 之后的版本起，列表最多列出 20 个文件。最后一行给出其余文件的数量，例如 `and 5 more`。

一个 `.wasm` 文件可能落入三种预算，所以建议会指出实际适用的那一个：`perfBudgets.runtime`、`perfBudgets.wasm` 或 `perfBudgets.public`。如果这个体积是有意为之，请调高该键，或把文件列入 `ignore`。

### 不合法的预算值

从 4.1.41 之后的版本起，生产构建会以代码 `E_CONFIG_LOAD` 拒绝不合法的 `perfBudgets` 值。更早的版本会丢弃或误读这样的值，且不给任何提示。

| `extension.config.js` 中的值 | 构建的行为 |
| ---------------------------- | ---------- |
| `perfBudgets` 不是对象，例如 `5` 或数组 | 停止：`perfBudgets in extension.config.js must be an object, found the number 5.` |
| 某个分类是字符串、`NaN`、`Infinity`、`0`、负数、`null` 或数组 | 停止：`perfBudgets.public in extension.config.js must be a finite number of bytes above 0, found the string "10".` |
| `ignore` 不是数组，或含有不是字符串的值 | 停止：`perfBudgets.ignore in extension.config.js must be an array of strings, found the string "assets/*.wasm".` |
| 既不是分类也不是 `ignore` 的键，例如 `ignored` | 警告一次，且不改变任何预算：`perfBudgets in extension.config.js declares a key nothing reads: ignored.` |
| `commands.dev` 下的 `perfBudgets` | 在 `dev` 中警告一次：`commands.dev.perfBudgets in extension.config.js has no effect: size budgets are checked on a production build only.` |

每条拒绝信息都会指出配置文件，并给出一个合法的示例。未知键的警告会列出可接受的键：`content-script`、`service-worker`、`page`、`shared`、`public`、`runtime`、`wasm`、`ignore` 和 `onExceed`。

预算设为 `0` 并不会关闭某个分类。要让某个文件不受预算约束，请把它列入 `ignore`。`ignore` 中的空白字符串会被跳过。

## 运维检查

- 在 CI 中运行多浏览器构建检查。
- 跟踪端到端 (E2E) 运行时长随时间变化的回归信号。
- 为关键扩展流程(安装、打开 UI、content script 激活) 添加冒烟测试。

## 常见的性能陷阱

- 大量 content-script bundle 在每个匹配页面上加载
- 没有守卫条件就在 `document_start` 做重活
- service worker 处理器进行非必要的同步初始化
- 即便只使用部分功能，UI 仍发布了庞大的全局 CSS/JS
