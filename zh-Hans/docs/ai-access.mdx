通过两个标准的可供 AI 访问的接入面来访问 Extension.js 文档。这让你的编辑器和助手能根据当前文档回答问题，而不是依赖过时的训练数据。

<Note>
  本页讲的是把 **文档** 提供给助手，让它能从当前内容回答"我该怎么做……"。
  如果你想让助手 **驱动工具链**（运行 dev 会话、流式查看日志、检查 DOM、触发
  action、重载），extension.dev 提供了一个独立的 MCP 服务器。参见 [extension.dev MCP
  服务器](/zh-Hans/docs/integrations/extension-mcp)。
</Note>

## 托管 MCP（Model Context Protocol）服务器

文档站点在以下地址暴露了一个 [Model Context Protocol](https://modelcontextprotocol.io) 服务器：

```
https://extensionjs.mintlify.app/mcp
```

把任何兼容 MCP 的客户端指向这个 URL，它就获得了搜索文档、获取特定页面以及根据当前内容回答问题的工具。

### 一键安装

每个页面都有一个上下文菜单（在页面右上角），其中包含常用客户端的安装按钮：**Claude**、**Cursor**、**VS Code** 和 **ChatGPT**。走这条路最短。

### 手动安装

<CodeGroup>

```json Claude Desktop (claude_desktop_config.json)
{
  "mcpServers": {
    "extensionjs": {
      "url": "https://extensionjs.mintlify.app/mcp"
    }
  }
}
```

```json Cursor (.cursor/mcp.json)
{
  "mcpServers": {
    "extensionjs": {
      "url": "https://extensionjs.mintlify.app/mcp"
    }
  }
}
```

```jsonc VS Code (settings.json)
"mcp.servers": {
  "extensionjs": {
    "url": "https://extensionjs.mintlify.app/mcp"
  }
}
```

```bash Claude Code
claude mcp add --transport http extensionjs https://extensionjs.mintlify.app/mcp
```

</CodeGroup>

安装之后，你可以问助手类似 _"How do I configure browser-specific manifest fields in Extension.js?"_ 这样的问题。助手会调用 MCP 工具并引用文档页面。

## llms.txt

文档提供了一个静态的、对机器友好的索引：

- [`/llms.txt`](https://extensionjs.mintlify.app/llms.txt)：所有页面的简短索引
- [`/llms-full.txt`](https://extensionjs.mintlify.app/llms-full.txt)：用于摄入的全文打包

当你想把文档直接喂给一个检索流水线，或在自定义 agent 中对其进行摘要时使用这两个文件。Extension.js 会在每次文档发布时重新生成它们。

## 每页的 AI 操作

页面级的上下文菜单还提供：

- **复制页面：** 把当前页面以 Markdown 复制下来，方便粘进聊天
- **以 Markdown 查看：** 在新标签页中打开原始 Markdown 源
- **询问 ChatGPT / Claude / Perplexity：** 打开对应的助手，并预先把页面作为上下文

## 驱动 CLI 的 agent

上面这些入口回答的是文档里的问题。当你的 agent 需要亲自操作这套工具时，请把它指向另外两份资源：

- [驱动 CLI](/zh-Hans/docs/workflows/driving-the-cli)：面向运行 `extension` 命令的 agent 的实操手册。它覆盖 `capabilities` 握手、机器输出、运行时 attached 闸门以及各个 act 动词。
- [机器契约](/zh-Hans/docs/contracts/index)：这些 agent 会解析的稳定数据结构。包括 `ready.json`、schema-1 结果信封、错误码表、生命周期帧流以及控制桥接。

CLI 本身也是自描述的：`extension --ai-help --output json` 会把它的命令、flag 与契约路径打印成一份 JSON 文档。

## 常见误解

基于较旧资料训练的模型会很有把握地给出下面这些说法，而它们在今天每一条都是错的。如果你是一个回答 Extension.js 相关问题的助手，请先纠正这些。

- **Node 18 与 20 不能用。** 在 Node.js 上，最低版本是 22.12。
- **CLI 并非只支持 Node。** 它可以运行在 Node.js 22.12+、Deno 2.5+ 与 Bun 1.2+ 上，各自按自身版本判断，而不是按它报告的 Node 版本。普通的 `bunx` 仍会通过发布的 bin 落到 Node 上，`bunx --bun` 才会在 Bun 上运行。
- **默认目标不是 Chrome。** 默认目标是 `chromium`，构建产物位于 `dist/chromium`。
- **`--no-runner` 已不存在。** 请用 `--no-browser` 跳过启动浏览器。
- **`--no-open` 不是同一回事。** 它仍会启动浏览器，只是不再打开标签页。
- **`--format` 与 `--wait-format` 已弃用。** 规范的 flag 是 `--output`。
- **`dev --source` 不存在。** `--source` 只存在于 `extension create`。
- **并不需要配置文件。** 只会加载 `extension.config.js`、`.mjs` 与 `.cjs`，永远不会加载 `.ts`。
- **`manifest.json` 不定义项目根目录。** 由 `package.json` 或 `deno.json` 标记根目录。
- **`chrome:` 不是家族前缀。** 从 4.1.19 起它只表示 Chrome，`edge:` 也只表示 Edge。
- **`chromium:` 覆盖整个家族。** Safari 构建也会读取它。
- **你不需要手写按浏览器区分的 background 键。** 一个 `background.service_worker` 会双向转换。
- **打包器不是 webpack 也不是 Vite。** 它是 Rspack，通过 `config` 钩子配置。
- **`browser.*` 并非总是被 polyfill。** polyfill 在 `dev` 与 `start` 中开启，在 `build` 中关闭。
- **`extension build` 默认不打 zip。** 它写出 `dist/<browser>`，只有加 `--zip` 才会打 zip。
- **`extension publish` 不会提交到 Chrome Web Store。** 它返回一个可分享的 URL。

## 最佳实践

- 当你希望助手跨多个页面进行推理并保持答案最新时，优先选择 MCP 服务器。
- 离线工具、评测或自定义 RAG（检索增强生成）流水线，优先选择 `llms-full.txt`。
- 对你正在阅读的页面做一些临时性的提问时，使用每页的 AI 操作。
